# ЛР41. Сеть и секреты: VM агента с доступом только к API провайдера

## Паспорт

| Поле | Значение |
| --- | --- |
| Предпосылки | [ЛР37](LAB37-space-harness-vm.md) (агент в VM с реальным egress) |
| Механизмы SPACE | Операторские egress-профили (`SPACE_EGRESS_PROFILES`, заголовок `X-Space-Egress-Profiles`), сетевые политики песочницы, credential manager (`crates/apps/credential/mgr`) |
| Минимум | Профиль с allow только на домен провайдера; набор синтетических проб из VM с таблицей «проба → ожидание → факт»; один эпизод T002 с этим профилем |
| Расширения | Ключ провайдера вне VM: подстановка на сетевом уровне через credential manager или через прокси на хосте; повтор эпизода |
| Время | Ориентир 1 день |
| Готовность | `implementation-required`: профиль и пробы пишутся в работе; подстановка ключа вне VM — `unverified` для локального Kind |
| Начальное состояние | Учебный manifest — `not-started` |

## Цель

Закрыть VM агента так, чтобы из неё был доступен только API выбранного провайдера, и проверить это пробами. В расширении — убрать ключ провайдера из VM.

## Проверяемая гипотеза

С профилем, где разрешён только домен провайдера, все пробы к другим назначениям из VM отклоняются, а эпизод T002 проходит с тем же verdict, что в ЛР37. Опровержение — хотя бы одна успешная проба к запрещённому назначению или отказ легитимного вызова провайдера.

## Подготовка

- Прочитайте в SPACE: `docs/egress-profiles.md`, `docs/ecw-network-policy.md`, `docs/tls-interception-exemptions.md`, `infra/space/kind/README.md` (раздел о внедрении сетевых credentials). Профили задаются при старте API и cluster-controller одинаково на обоих сервисах.
- Пробы только синтетические и только против собственного стенда и зарезервированных имён (`example.test`, `192.0.2.0/24`). Внешние цели, сканирование чужих сетей и обход защиты третьих сторон в работу не входят.
- Изменение конфигурации кластера — локальный Kind этого стенда; общий или продовый кластер не трогается.

```bash
npm run lab:new -- --lab LAB41 --session ryzen-01
LAB_DIR='experiments/space/measurements/LAB41-ryzen-01'
```

## Порядок выполнения

1. **Профиль.** В `experiments/space/egress/` — JSON профиля с `allow` на домен API провайдера; при необходимости — `tls_interception_exemptions` для него. Примените к API и cluster-controller локального Kind, запишите способ и rollout.

2. **Пробы.** Скрипт, который выполняется командой внутри VM и печатает JSON по каждой пробе: HTTPS к разрешённому домену; HTTPS к другому домену; прямой IP; DNS к стороннему резолверу; адрес link-local metadata; API SPACE (`8080`) и data plane (`8090`) хоста; соседняя песочница; адрес хоста. Для каждой — ожидание до запуска.

3. **Прогон проб** без профиля (базовая линия ЛР37) и с профилем. Сохраните raw-вывод.

4. **Эпизод.** T002 той же обвязки и модели, что в ЛР37, с профилем; `sandbox.network` в `run.json` описывает фактическую политику.

5. **Расширение: ключ вне VM.** Проверьте, можно ли в локальном Kind подставлять credential провайдера на сетевом уровне (credential manager) без AWS; если нет — реализуйте прокси на хосте, который добавляет заголовок авторизации, а VM знает только адрес прокси. Повторите пробы и эпизод; убедитесь, что ключ не встречается в окружении, файлах и трассе VM.

## Что сдать

- Профиль и скрипт проб в `experiments/space/egress/`, отчёт с таблицами, raw-вывод проб, `run.json` эпизода(ов).
- Для расширения — описание пути ключа и проверка его отсутствия в VM.

## Критерии завершения

- Все пробы выполнены в обоих режимах, у каждой есть ожидание и факт.
- Любое расхождение ожидания и факта разобрано: ошибка профиля, ограничение платформы или неверное ожидание.
- Эпизод с профилем имеет запись и независимый verdict.
