## Цель

Научиться управлять общим GPU-флотом как владелец платформы: просить устройства по атрибутам через DRA, делить флот между командами квотами, запускать распределённые job'ы «все или ничего» и видеть, как обучение переживает потерю pod. Всё это проверяется на фиктивных устройствах, потому что логика планировщика не зависит от того, настоящий ли GPU.

## Проверяемая гипотеза

1. DRA-claim с CEL-селектором по атрибуту устройства размещается только на подходящих фиктивных GPU, а невыполнимый claim оставляет pod в `Pending` с понятным событием.
2. На одном и том же потоке job'ов cohort с одалживанием в Kueue повышает среднюю занятость фиктивных GPU по сравнению со строгими квотами не меньше чем на X процентных пунктов, при этом время ожидания самого большого job'а растёт не больше чем в Y раз.
3. DDP job на CPU через JobSet после убийства одного worker'а перезапускается и продолжает обучение с последнего чекпойнта, теряя не больше одного интервала чекпойнта.

X, Y и интервал чекпойнта фиксируются в протоколе до первого прогона.

## Подготовка

- Прочитайте: документацию Kubernetes по Dynamic Resource Allocation; репозитории `kubernetes-sigs/dra-example-driver`, `kubernetes-sigs/kwok`, `kubernetes-sigs/kueue` (ClusterQueue, LocalQueue, cohort, preemption, Topology Aware Scheduling), `kubernetes-sigs/jobset`; release notes Kubernetes 1.37 по gang scheduling (KEP 4671, бета).
- Версия Kubernetes в Kind — не ниже 1.34 (DRA GA). Нужен ли feature gate для gang scheduling в выбранной версии, проверьте по release notes и запишите.
- Закрепите версии Kind, node image, example driver, KWOK, Kueue, JobSet.
- Генератор потока job'ов детерминирован (фиксированный seed) и лежит в `experiments/k8s-gpu/sim/`.

## Порядок выполнения

1. **Часть A: DRA.** Kind-кластер с `dra-example-driver`, который публикует фиктивные GPU с атрибутами. Напишите и примените:
   - claim на одно устройство с атрибутом памяти не меньше порога;
   - claim на два устройства одного узла;
   - ResourceClaim, общий для двух pod;
   - заведомо невыполнимый claim.
   Сохраните `ResourceSlice`, `DeviceClass`, claim'ы, события и итоговое размещение.
2. **Часть B: флот и квоты.** Отдельный Kind-кластер, 8 KWOK-узлов с extended resource `example.com/gpu: 8` и метками `rack`, `block`. Stage-ресурсы KWOK задают длительность «обучения» pod. Установите Kueue: три LocalQueue для команд `research`, `product`, `eval`, по ClusterQueue на команду.
   - Прогон B1: строгие квоты без cohort.
   - Прогон B2: тот же поток job'ов, общий cohort с borrowing и preemption.
   Поток: долгие job'ы по 16–32 «GPU» у `research`, короткие по 1–4 у `product` и `eval`, общая длина серии фиксирована. Каждую минуту снимайте занятость GPU и очередь по командам.
3. **Часть C (расширение): топология и gang.** Требование «все 16 pod в одном `block`» через Topology Aware Scheduling Kueue, затем нарочно фрагментируйте флот мелкими job'ами. Отдельно попробуйте нативный gang scheduling Kubernetes 1.37 и сравните поведение при нехватке мест.
4. **Часть D: обучение и отказ.** JobSet с PyTorch DDP на CPU (backend `gloo`), 2–4 worker'а, маленькая модель на синтетических данных, чекпойнт каждые N шагов в общий том. В середине обучения удалите один pod. Запишите: когда job это заметил, сколько занял перезапуск, с какого шага продолжил, сколько шагов потеряно.
5. **Teardown.** Удалите оба Kind-кластера.

- Все четыре claim части A сопоставлены с ожиданием.

- Часть D показала перезапуск и потерю шагов в цифрах.
