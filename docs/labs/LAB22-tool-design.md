# ЛР22. Как интерфейс инструментов влияет на работу агента

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип | Инженерное расширение и парное сравнение интерфейсов |
| Время | 3–6 часов реализации и проверки; затем 6 попыток и независимая оценка |
| Предпосылки | ЛР09; понимание разрешённых действий выбранной задачи |
| Готовность | `implementation-required`: унифицированного переключателя shell/structured-tools в текущем runner нет |
| Минимальный объём | Одна задача × одна обвязка/модель × два интерфейса × три пары = 6 новых попыток |
| Расширение | Отдельные серии с разной подробностью schema или объёмом tool result |

## Цель

Проверить, помогает ли специализированный интерфейс агенту выбирать и выполнять нужные операции. Отличить эффект интерфейса от расширения полномочий, скрытой подсказки решения и дополнительного объёма возвращаемых данных.

## Проверяемая гипотеза

«При одинаковом наборе разрешённых операций структурированный интерфейс уменьшает ошибки вызова без снижения успешности задачи». Фактор — способ выражения операции: командная строка либо named tool с JSON arguments. Работа инструмента, начальные файлы, модель, бюджет, содержимое результатов, ограничения и judge одинаковы.

Пилотное правило: число pass не уменьшается, а суммарное число определённых заранее ошибок вызова меньше; ошибки границ не допускаются в обоих вариантах. Три пары не дают доказательства универсального преимущества. Снижение числа вызовов само по себе не считается улучшением, если итог хуже.

## Подготовка

```bash
npm run lab:new -- --lab LAB22 --session tools-pilot
LAB_DIR='experiments/local-models/measurements/LAB22-tools-pilot'
npm run lab:practice -- --scenario tool-success --session tools-pilot
npm run check
```

Разберите [синтетический trace](practice.md): tool call ID, имя, arguments, результат и продолжение модели. Это готовое учебное упражнение без API; оно не проверяет способность реального агента выбрать инструмент. Сохраните ссылку на его synthetic manifest в отчёте, `run_ids` для него не создавайте.

Основной эпизод — [миграция API](episodes/interface-migration/episode.md) или существующая T002. Публичная миграция сначала требует регистрации нового task ID. На T002 сохраняются контракт, seed и внешний judge. Состав native tools выбранного harness и возможность убрать дублирующие инструменты проверяются по точной версии; не предполагается, что все девять обвязок имеют одинаковые hooks/MCP/tool registry.

## Порядок выполнения

1. **Определите одинаковые полномочия.** До реализации составьте список операций, нужных для эпизода: прочитать файл, найти текст, применить изменение к разрешённому файлу, запустить разрешённую проверку. Ограничения путей, входных размеров, subprocess и сети совпадают. Сравнение unrestricted shell со строго ограниченными четырьмя tools меняет сразу интерфейс и возможности; его нельзя выдавать за минимальный опыт.

2. **Реализуйте два представления одной функции исполнения.** В командном варианте агент вызывает небольшой CLI с явными подкомандами; в структурированном — tools `read_file`, `search_text`, `apply_edit`, `run_check`. Это проектируемые интерфейсы, а не уже существующие команды репозитория. Оба пути вызывают одну проверяемую реализацию, получают одинаковые ошибки и результаты. Названия инструментов не должны раскрывать готовый патч или местоположение неисправности. Контракт задаёт разрешённые действия, а не последовательность решения.

3. **Подготовьте инженерный допуск в одном harness.** Зарегистрируйте tools/командный facade, отключите обход через вторую эквивалентную native возможность или явно признайте эксперимент наблюдательным. Зафиксируйте schemas, help text, handler hashes, лимиты вывода и режим в запечатанных controls и run identity. Сохраните native adapter до/после и запись предположения в ledger. `--variant without-spec` для этого не подходит; новые параметры сначала реализуются и тестируются.

4. **Докажите равенство операций offline.** Для каждого разрешённого действия подайте одинаковый набор входов через оба пути и сравните изменение workspace, exit/result и содержание ответа. Включите несуществующий файл, неверный тип поля, путь за пределами workspace, конфликт patch и вывод длиннее лимита. Лимит и правило усечения одинаковы; сообщается сам факт усечения. Запрет операции исполняет handler/граница, а не текстовая просьба модели. Не ослабляйте текущие Docker/network walls.

5. **Назначьте кодировку ошибок и правило остановки.** До серии задайте категории: неизвестный инструмент, неверная schema/CLI syntax, запрещённый путь, ошибка выполнения при корректном запросе, корректный вызов с неверной целью. Эти случаи не смешиваются. Ошибка модели считается только при полном trace; потерянный tool result — проблема наблюдаемости. Остановка — verdict-ready, общий timeout, исчерпание бюджета либо нарушение границы. Последнее прекращает серию до исправления механизма.

6. **Зафиксируйте три пары и все константы.** Порядок CLI → structured, structured → CLI, CLI → structured. Один точный model ID, harness image, task/seed, разрешённые operations, токеновый/временной бюджет, sampling, содержимое исходного prompt. Help/schema различаются как часть вмешательства и хешируются. Их токены учитываются: обширная schema не бесплатна. Пилот для отладки протокола не входит в эти шесть попыток.

7. **Исполните только после допуска.** Создайте настоящие записи текущим жизненным циклом и реально принятым интерфейсом нового варианта. Сохраните команды в отчёте. Без инженерного расширения доступно только offline упражнение и проект механизма; отметьте `not-run` для агентной серии. Локальная модель дополнительно требует работающей ЛР08, подтверждённых tools и deployment identity.

8. **Оцените результат и вызовы.** Независимый judge проверяет артефакты без знания варианта. Аналитик trace размечает все tool calls по заранее заданным категориям и отдельно повторные обращения. При сомнении второй аналитик разбирает спорную строку. Показатели: verdict, ошибки каждого типа, исправление ошибки следующим вызовом, количество calls, суммарные input/output tokens, wall-clock. Размер JSON ответа инструмента в bytes можно измерить непосредственно; не называйте его токенами модели.

9. **Сравните пары и решите, что проверять дальше.** Покажите все исходы и ошибки, включая aborted. Улучшение только одного простого эпизода — основание для следующего опыта, а не для универсального отключения shell. Если хотите исследовать schema verbosity или `tool result` 2/8/32 KB, сделайте **новую серию с одним новым фактором**, неизменным интерфейсом и одинаковым полезным содержанием. Не меняйте schema, output cap и toolset одновременно в минимальном опыте.

## Что сдать

Протокол, карту эквивалентных операций, schemas/help/handler hashes, результаты offline equivalence tests, ledger row, все шесть run IDs и оценки, разметку trace, парный анализ и ограничения. Учебный trace из `lab:practice` хранится как synthetic evidence, отдельно от экспериментальных результатов. Проверка комплектности — [report-validation.md](report-validation.md).

## Критерии завершения

- [ ] Минимальная серия меняет интерфейс, сохраняя полномочия и реализацию операций.
- [ ] Обход второго toolset исключён или работа честно отмечена как иной, несопоставимый дизайн.
- [ ] Схемы и вмешательство версионированы, условия отражены в controls/record/compare.
- [ ] Три пары и категории ошибок заданы до запуска.
- [ ] Сохранены все попытки, независимые verdict и полная разметка вызовов.
- [ ] Стоимость описаний tools и исправлений учитывается; неизвестные метрики не заменены нулями.
- [ ] Невыполненная инженерная часть не названа измерением; `npm run check` проходит.

## Контрольные вопросы

1. Почему unrestricted shell и четыре разрешённых tools меняют больше одного фактора?
2. Где должна исполняться проверка пути: в описании инструмента или handler?
3. Чем неверный тип аргумента отличается от корректного запроса несуществующего файла?
4. Можно ли считать более короткий tool result улучшением, если он скрывает нужное доказательство?
5. Почему описание инструментов необходимо включать в бюджет?
