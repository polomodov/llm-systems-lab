# ЛР09. Пилот и сравнительная кампания автономных агентов

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип работы | Измерительная: реальные попытки, независимая оценка и сравнение одинаковых условий |
| Время | Ориентир 2–4 часа оператора для cloud или 4–8 для local плюс исполнение и оценка; 12 cloud попыток при timeout 900 s — до 3 часов agent execution без setup/review |
| Предпосылки | ЛР01 и индивидуальные ЛР11–19 выбранных обвязок; для local дополнительно завершённая ЛР08 на каждой включаемой обвязке и готовая конфигурация модели |
| Готовность | Cloud lifecycle реализован; реальный аккаунт/модель проверяются перед запуском. Локальная серия **conditional**, до приёмки ЛР08 её запуск недоступен |
| Минимальный облачный объём | 3 pilot + 9 новых попыток: три обвязки × одна общая модель/provider × T002 × 3; подходящие pilot можно взять из ЛР11–19 |
| Минимальный локальный объём | 4 pilot + 12 заранее назначенных сравнительных попыток: одна модель, T002, четыре основные обвязки |
| Расширение | 72 попытки T001/T002 для трёх финалистов; 36 T003 отдельно; облачная диагностика всех девяти — необязательна |

## Цель

Измерить, как разные обвязки выполняют один и тот же эпизод с фиксированной моделью и условиями. Отделить инженерную готовность от качества задачи, наблюдаемые значения от неизвестных, а контролируемое сравнение — от диагностики разных deployments.

## Проверяемая гипотеза

При одинаковых модели, входах, inference settings, лимитах и методе оценки выбранные обвязки могут различаться долей успешных троек, временем и необходимыми компонентами. Гипотеза проверяется для данной серии; отсутствие различия на трёх попытках не доказывает эквивалентность обвязок вообще.

## Подготовка

```bash
npm run lab:new -- --lab LAB09 --session my-session
LAB_DIR='experiments/local-models/measurements/LAB09-my-session'
npm run harnesses
npm run check
```

Заполните manifest и расписание попыток до первого исполнения. Выберите один проверенный model deployment и общий timeout, например 900 s; лимиты задачи прочитайте из открытого контракта. Сохраните версии обвязок, immutable image IDs, режим разрешений, budget policy и метод судейства. Фактические provider credentials подготовьте в `.env` без вывода значений в отчёт.

**Cloud — самостоятельный основной маршрут без ЛР08.** Выберите три обвязки с общим реально доступным provider/model ID. Например, профили Claude Code, OpenCode и Pi допускают Anthropic; Pi, mini-SWE-agent и OpenHands допускают также общую ветвь OpenAI. Это пересечение возможностей текущих профилей, а не гарантия доступа аккаунта к модели. Используйте индивидуальные работы из [каталога ЛР11–19](README.md) для образов, provider, smoke и особенностей трасс. Выполненная там T002 может стать pilot, если её фактические условия подходят; сравнительная тройка всегда новая. Amp и неподтверждённый Copilot selector исследуются отдельно и не добавляются в exact-model группу ради третьей строки.

Запишите выбранный маршрут (`cloud` или `local`) и обязательный объём в учебный отчёт. Если общего deployment для трёх обвязок нет, диагностический отчёт по разным моделям остаётся полезным, но не заменяет минимальное контролируемое сравнение.

Для local core используются Pi, mini-SWE-agent, OpenCode и OpenHands. Каждый должен отдельно пройти ЛР08; наличие `local:plan` не означает готового подключения. Codex — дополнительная ветвь после собственной проверки. Claude Code, Antigravity, Copilot и Amp не получают локальный маршрут автоматически.

## Порядок выполнения

1. **Выберите объём и зафиксируйте порядок.** Не запускайте всю матрицу до пилота. Сохраните в отчёте таблицу запланированных слотов и правило остановки. Основной минимум и расширения:

   | Серия | Состав | Число попыток | Назначение |
   | --- | --- | --- | --- |
   | Cloud pilot | 3 выбранные обвязки × 1 общая модель/provider × T002 | 3; допускаются подходящие ЛР11–19 | Допуск в облачное сравнение |
   | Cloud минимум | 3 × 1 × T002 × 3 | 9 новых | Самостоятельная сдача ЛР09 без local bridge |
   | Pilot core | 4 обвязки × 1 модель × T002 × 1 | 4 | Проверить реальный lifecycle и протокол |
   | Local минимум | 4 × 1 × T002 × 3 | 12 новых | Сравнить заранее назначенные тройки |
   | Добавление T001 | 4 × 1 × T001 × 3 | Ещё 12 | Досье на одном frozen archive |
   | Полная основная серия | 4 × 3 модели × T001/T002 × 3 | 72 всего | Расширение до трёх финалистов; уже выполненные подходящие слоты не дублируются |
   | Аудит T003 | 4 × 3 × T003 × 3 | 36 отдельно | Диагностика, не причинный рейтинг обвязок |
   | Cloud coverage всех harness | 9 обвязок × свой доступный provider/model × T002 × 1 | 9 pilot из ЛР11–19 для полного harness-маршрута | Проверка deployment; отдельная от same-model сравнения |

   Pilot не включайте задним числом в сравнительные тройки. Техническая несовместимость до старта задачи учитывается отдельно; медленная модель не исключается только за скорость. Заранее выберите порядок обвязок по раундам, чередуя первую/последнюю. Для обеих серий выполняйте одну попытку за раз; в local используйте один model server и один slot на Ryzen.

2. **Проверьте облачный охват при необходимости.** Девять поддержанных адаптеров: `claude-code`, `opencode`, `codex`, `antigravity-cli`, `pi`, `mini-swe-agent`, `openhands`, `copilot-cli`, `amp`. Для каждого выберите только provider из `npm run harnesses` и доступный точный ID по README адаптера/аккаунту. У Amp используйте поддерживаемый `managed:<mode>`; underlying модель не объявляйте известной. Copilot selector также не равен доказанному snapshot. Эти девять строк не обязаны использовать одну модель и не образуют честного same-model рейтинга. Для контролируемой cloud подсерии берите только пересечение реально доступных model IDs и одинакового provider.

3. **Создайте новую запись для одного слота.** Ниже показан **существующий cloud CLI**; замените все значения в угловых скобках перед выполнением. Для локальной серии используйте документированный и проверенный интерфейс, реализованный в ЛР08: этот текст не вводит работающего `--local` или готового `--provider local`.

   ```bash
   HARNESS_ID='pi'
   PROVIDER_ID='anthropic'
   MODEL_ID='<точный доступный model ID>'
   IMAGE_REF='<проверенный image tag или image ID>'
   PROXY_IMAGE_REF='<один закреплённый proxy image ID для серии>'
   npm run new-run -- --harness "$HARNESS_ID" --agent a2-janitor --task T002 --provider "$PROVIDER_ID" --model "$MODEL_ID"
   ```

   Перенесите выведенный run ID в соответствующий слот и в переменную. ID не придумывают и не используют повторно:

   ```bash
   RUN_ID='<ID, выданный new-run>'
   npm run prepare-run -- --run "$RUN_ID" --variant baseline --provider "$PROVIDER_ID"
   ```

4. **Зафиксируйте входы T001/T002/T003.** Для T002 оставьте один seed commit, одинаковый контракт и исходные файлы. Для T001 сначала возьмите архив `trace/sources.jsonl` из зарегистрированного discovery run; если его ещё нет, выполните один отдельный live T001 и сохраните его как источник архива, вне controlled series. Архив должен содержать тела и статусы ответов, не только URL. Используйте один и тот же архив и `as-of` во всех сравниваемых попытках:

   ```bash
   SOURCE_ARCHIVE='<путь к trace/sources.jsonl discovery run>'
   AS_OF_DATE='<общая дата YYYY-MM-DD>'
   npm run prepare-run -- --run "$RUN_ID" --variant baseline --provider "$PROVIDER_ID" --as-of "$AS_OF_DATE" --source-archive "$SOURCE_ARCHIVE"
   ```

   Это альтернативная подготовка **новой T001-записи** с `a1-dossier`, а не повторный prepare уже подготовленного T002. Replay не подгружает отсутствующие ответы из интернета. Для T003 используйте `a3-ledger-auditor`: setup копирует конфигурацию выбранной обвязки, поэтому разные harness имеют разные входы; вынесите эту серию в диагностический раздел.

5. **Исполните попытку и проверьте состояние.** Существующая команда cloud run:

   ```bash
   npm run run -- --run "$RUN_ID" --image "$IMAGE_REF" --proxy-image "$PROXY_IMAGE_REF" --model "$MODEL_ID" --provider "$PROVIDER_ID" --timeout 900 --budget-mode observed
   ```

   Восемь адаптеров требуют `observed`, так как проверенного hard USD cap у них нет. Если сравниваете их с Claude, явно используйте общую политику; отдельно исследуемые `hard`-попытки в ту же группу не включайте. `observed` означает исследовательское отклонение от контрактного USD cap; timeout остаётся принудительным пределом. Native turns/iterations разных систем не являются одинаковыми единицами. Не меняйте модель, provider, исходные файлы или запечатанный snapshot после prepare.

6. **Передайте результат независимому оценщику.** Нормальная последовательность: `planned → prepared → running → awaiting_review → completed`. Exit 0 не означает pass. При `aborted` сохраните причину и не запускайте judge как способ превратить ошибку в completed. Для `awaiting_review` создайте чистый JSON-шаблон:

   ```bash
   (
     set -o noclobber
     npm run --silent evaluation-template -- --run "$RUN_ID" > "$LAB_DIR/raw/evaluation-$RUN_ID.json"
   )
   ```

   Оценщик работает вне agent container, не изменяет артефакты и не передаёт агенту скрытые проверки. Он заполняет `result` (`pass`, `fail`, `partial`), `evaluator`, `check_output`, при необходимости `human_notes`, сохраняя generated hashes. Для T002 применяется внешний hidden-check; для T001/T003 — rubric, причём T001 использует также предусмотренный проверяющий скрипт. Конкретный способ запуска скрытого оценщика задаёт оператор; здесь не предполагается универсальная существующая команда для всех задач. Если независимый оценщик недоступен, запись остаётся `awaiting_review`.

   ```bash
   npm run judge-run -- --run "$RUN_ID" --evaluation "$LAB_DIR/raw/evaluation-$RUN_ID.json"
   npm run check
   ```

   `judge-run` связывает оценку с manifests и проверяет целостность; содержательное решение он сам не выносит. Учебный отчёт лишь ссылается на полученный record.

7. **Закройте pilot и заморозьте сравнительную серию.** По трём cloud или четырём local pilot зафиксируйте protocol/timeout/identity ошибки. Исправление адаптера или backend создаёт новую конфигурацию и новые попытки. После исправлений сформируйте девять cloud или двенадцать local слотов; выполняйте их последовательно, получая новый run ID для каждого. Не отбрасывайте начатые ошибки и не подменяйте неудачную попытку успешным retry. Остановите расширение, если основной протокол ещё нарушается, памяти недостаточно или нет независимого judge; причину включите в отчёт.

8. **Сравните только заявленные run IDs.** Составьте строку из реальных ID без пробелов после запятых. Не используйте общий каталог по умолчанию, если в нём есть discovery, pilot или иные исследования:

   ```bash
   SERIES_RUN_IDS='<run-id-1>,<run-id-2>,<остальные ID серии>'
   npm run --silent compare -- --runs "$SERIES_RUN_IDS" > "$LAB_DIR/raw/compare.json"
   npm run check
   ```

   Проверьте `pending`, `excluded`, причины разных `conditions` и долю наблюдённых model IDs. Compare строит тройки внутри группы/harness в порядке run ID; для минимальной серии каждая содержит ровно заранее выбранные три попытки. Начатые aborted входят в знаменатель; записи без начала исполнения отдельно исключены. Не объединяйте группы вручную лишь для получения одной диаграммы. Локальные условия должны разделяться реализацией ЛР08.

9. **Интерпретируйте результат и решите об расширении.** Запишите pass/total, `pass@3`, `pass^3`, время с measured/total и недоступные метрики. При трёх попытках показывайте исходные исходы, а не уверенный глобальный рейтинг. Сравните успешность и время, затем измеренную память и энергию; неизвестный показатель не может служить основанием победы. Полная серия 72 является расширением, а не обязательным условием первой сдачи. Сохраните критерий отбора финалистов до запуска расширения. Не смешивайте 36 T003 с 72 основными попытками.

10. **Запишите, что понадобилось обвязкам.** В `experiments/<harness>/NOTES.md` добавьте реальные run IDs, условия, ошибки и необходимые изменения. Новые компоненты получают ledger row в том же изменении; простое отсутствие pass не обосновывает добавление нового компонента. Из неизвестной cloud стоимости не делайте 0. В локальной серии inference fee, энергия и амортизация — разные величины; 0 inference fee требует подтверждённого local-only пути, а электричество требует измерения и тарифа.

## Что сдать

- Manifest, заранее заданную матрицу слотов и учебный отчёт с raw compare JSON.
- Ссылки на все созданные run records, включая discovery, pilot, aborted, pending и основную серию.
- Независимые оценки с идентификатором судьи и привязкой к неизменным результатам.
- Таблицу сопоставимых групп, ограничения вывода, NOTES/ledger additions при изменении компонентов.

## Критерии завершения

- [ ] Готовность каждой обвязки и модельного deployment проверена до серии.
- [ ] Pilot отделён от заранее назначенных сравнительных попыток.
- [ ] Выбран маршрут: для cloud выполнены 9 сравнительных попыток после трёх pilot; для local — 12 после четырёх pilot. Меньший объём обозначен как промежуточный отчёт.
- [ ] Все начатые ошибки сохранены; нет заменённых задним числом исходов.
- [ ] T001 использует единый frozen archive; T003 интерпретируется отдельно.
- [ ] `awaiting_review` не выдан за pass; независимый judge и evidence доступны для завершённых результатов.
- [ ] Compare выполнен на точных ID; model/deployment и другие conditions не смешаны.
- [ ] Стоимость и метрики без наблюдений не заменены нулями; `npm run check` проходит.

## Контрольные вопросы

1. Почему девять разных облачных providers/models дают coverage, но не чистый эффект harness?
2. Что изменится в выводе, если один T001 запущен live, а остальные replay?
3. Чем `pass@3` отличается от `pass^3`, и какие исходы дают разные значения?
4. Почему начатый timeout должен остаться в знаменателе?
5. Что именно мешает причинно сравнивать T003 между разными обвязками?
