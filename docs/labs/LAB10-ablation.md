# ЛР10. Парная абляция спецификации и решение по реестру

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип работы | Контролируемый эксперимент: удалить один компонент prompt и сравнить парные тройки |
| Время | Ориентир 2–4 часа оператора плюс исполнение и независимая оценка; шесть запусков по timeout 900 s — до 90 минут agent execution без setup/review |
| Предпосылки | Завершённая cloud либо local ЛР09; проверенный deployment и независимый оценщик |
| Готовность | Варианты `baseline` и `without-spec` реализованы; локальная ветвь требует готовой ЛР08 |
| Минимальный объём | Одна обвязка × одна модель × одна задача × два варианта × три повтора = 6 новых попыток |
| Расширение | Повтор на второй задаче или второй обвязке после завершения первой серии |

## Цель

Измерить вклад текста независимой спецификации агента в prompt и принять ограниченное данными решение о компоненте. Сохранить неизменными контракт, инфраструктурные границы и все остальные условия.

## Проверяемая гипотеза

Добавление спецификации к контракту улучшает исходы выбранной задачи при фиксированных модели и обвязке. Проверяемое воздействие: в `baseline` prompt содержит spec + task, в `without-spec` — task без добавленного блока spec. Улучшение должно быть видно в заранее выбранных парных попытках, а не в отобранных после исполнения удачных примерах.

Нулевое различие в трёх парах означает отсутствие обнаруженного эффекта в этой малой серии, а не доказательство ненужности спецификации во всех задачах. Оба варианта с тремя fail могут показывать слишком трудную задачу или проблему протокола.

## Подготовка

```bash
npm run lab:new -- --lab LAB10 --session my-session
LAB_DIR='experiments/local-models/measurements/LAB10-my-session'
npm run check
```

Выберите одну завершённую конфигурацию ЛР09. Зафиксируйте model/deployment identity, provider, версию и image ID обвязки, context/output, sampling/reasoning, timeout, budget policy, seed commit или source archive и метод judge. Для первого опыта рекомендуется T002: её исходные файлы воспроизводимы. Заполните три пары и порядок вариантов до запуска.

Облачный маршрут выполняется текущими командами без ЛР08 и без Ryzen. Команды сборки, smoke и особенности выбранной обвязки возьмите из её [индивидуальной ЛР11–19](README.md); процедуру оценки — из [общего порядка](harness-workflow.md). Основной пример ниже использует Pi; для другой обвязки замените harness/provider/model/image и proxy image её фактическими условиями. Managed Amp допускает абляцию при одном mode, но такая дополнительная серия не утверждает неизменность underlying модели и не заменяет контроль с exact model.

## Порядок выполнения

1. **Сформулируйте единственное вмешательство.** Прочитайте реализацию `prepareRun` и убедитесь, что `without-spec` убирает только добавленный текст спецификации из `prompt.txt`. `inputs/spec.md` остаётся частью доказательного snapshot; task contract, Docker wall, gateway, timeout и внешняя оценка сохраняются. Не удаляйте файлы из `agents/`, не редактируйте `tasks/*/task.md`, не читайте hidden checks. Другие абляции сейчас не реализованы этой командой.

2. **Назначьте парный порядок и основные показатели.** Минимальная схема: пара 1 `baseline → without-spec`, пара 2 `without-spec → baseline`, пара 3 `baseline → without-spec`. При расширении балансируйте порядок дальше. Каждый запуск получает чистый workspace и новый ID. Основной показатель — независимый verdict; дополнительные — pass@3, pass^3 и время. Заранее укажите правило работы с aborted и отсутствующими метриками. Seed используйте одинаково внутри пары только если backend действительно поддерживает его; не приписывайте облачному API детерминизм.

3. **Подготовьте первый baseline.** Пример использует **существующий cloud CLI**; заполните значения из выбранной серии. Для local используйте реально принятый интерфейс ЛР08 и те же записанные условия, не выдумывая новые флаги.

   ```bash
   HARNESS_ID='pi'
   PROVIDER_ID='anthropic'
   MODEL_ID='<точный ID из выбранной серии>'
   IMAGE_REF='<тот же image ID, что в выбранной серии>'
   PROXY_IMAGE_REF='<тот же proxy image ID, что в выбранной серии>'
   npm run new-run -- --harness "$HARNESS_ID" --agent a2-janitor --task T002 --provider "$PROVIDER_ID" --model "$MODEL_ID"
   BASELINE_RUN_ID='<новый ID, выданный new-run>'
   npm run prepare-run -- --run "$BASELINE_RUN_ID" --variant baseline --provider "$PROVIDER_ID"
   ```

4. **Подготовьте парный without-spec как новую запись.** Не переиспользуйте baseline ID и не правьте его `inputs/control/prompt.txt`:

   ```bash
   npm run new-run -- --harness "$HARNESS_ID" --agent a2-janitor --task T002 --provider "$PROVIDER_ID" --model "$MODEL_ID"
   ABLATION_RUN_ID='<другой новый ID, выданный new-run>'
   npm run prepare-run -- --run "$ABLATION_RUN_ID" --variant without-spec --provider "$PROVIDER_ID"
   ```

   Проверьте оба `inputs/manifest.json`: один и тот же task, provider, seed commit, начальные файлы вне служебной `.git`; различается `variant` и сформированный prompt. Полные manifest/prompt hashes не обязаны совпадать: они отражают вмешательство и разные run IDs. Нельзя удалять эту разницу из evidence ради совпадения hash.

5. **Исполните варианты в назначенном порядке.** Пример команды для каждого выбранного ID:

   ```bash
   RUN_ID="$BASELINE_RUN_ID"
   npm run run -- --run "$RUN_ID" --image "$IMAGE_REF" --proxy-image "$PROXY_IMAGE_REF" --model "$MODEL_ID" --provider "$PROVIDER_ID" --timeout 900 --budget-mode observed
   ```

   Перед вторым исполнением присвойте `RUN_ID="$ABLATION_RUN_ID"` и повторите ту же команду. Для пар 2 и 3 создайте ещё четыре новые записи шагами 3–4, исполните их по плану. Не исправляйте адаптер между вариантами одной серии; необходимое исправление завершает текущую конфигурацию и требует новой серии. Не меняйте budget policy ради одного варианта. Параметры native limits и их ограничения сохраните из ЛР09.

6. **Получите независимые оценки без подсказки о варианте.** По возможности показывайте судье результаты под нейтральными обозначениями; соответствие run ID сохраняйте у координатора. При `awaiting_review` создайте шаблон, заполните его через внешнего оценщика и примените:

   ```bash
   (
     set -o noclobber
     npm run --silent evaluation-template -- --run "$RUN_ID" > "$LAB_DIR/raw/evaluation-$RUN_ID.json"
   )
   ```

   ```bash
   npm run judge-run -- --run "$RUN_ID" --evaluation "$LAB_DIR/raw/evaluation-$RUN_ID.json"
   npm run check
   ```

   Между командами оценщик должен заполнить result/evaluator/check_output, сохранив artifact/workspace hashes. T002 использует hidden-check вне agent container. `aborted` остаётся ошибкой исполненной попытки и не проходит через judge; `awaiting_review` без судьи не получает придуманного verdict. Ссылки на оценки и raw traces внесите в таблицу пар.

7. **Учтите особенности других задач при расширении.** Для T001 оба prepare получают одинаковые `--as-of` и `--source-archive`, взятые из ЛР09. Live discovery не входит в эту абляцию. Для T003 одна и та же обвязка даёт одинаковый аудируемый набор исходников, но естественные файлы спецификации/конфигурации из workspace не удаляются `without-spec`. Здесь проверяется только дополнительный блок prompt; это не эксперимент «агент нигде не видит спецификацию». Между разными обвязками T003 не является одинаковым входом.

8. **Постройте отчёт по шести настоящим ID.** Заполните две строки ровно тремя ID каждого варианта, без пробелов после запятых:

   ```bash
   BASELINE_RUN_IDS='<baseline-1>,<baseline-2>,<baseline-3>'
   ABLATION_RUN_IDS='<without-spec-1>,<without-spec-2>,<without-spec-3>'
   npm run --silent compare -- --runs "$BASELINE_RUN_IDS,$ABLATION_RUN_IDS" > "$LAB_DIR/raw/compare.json"
   npm run check
   ```

   Compare сохраняет baseline/without-spec в разных groups. Это ожидаемо: он не вычисляет причинный эффект автоматически. Проверьте, что остальные существенные conditions совпадают; для local — также deployment fingerprint из ЛР08. Укажите любые `pending`/`excluded`, не превращайте их в pass или в молчаливое удаление. CLI собирает тройки по run ID внутри группы; парное соответствие восстанавливайте по заранее заполненной таблице, а не по сортировке общего списка.

9. **Вычислите ограниченный вывод.** Для каждого варианта покажите три исхода, pass/3, pass@3 и pass^3. Для каждой пары покажите смену исхода и разность wall-clock при наличии обоих измерений; не сравнивайте неизвестную стоимость с числом. Возможны разные выводы: спецификация помогает; явного эффекта нет; меньше текста улучшает результат; данных недостаточно из-за технической ошибки. Объясните каждое утверждение конкретными run IDs и артефактами. Не объявляйте статистическую значимость по одной тройке и не переносите вывод на другие модели.

10. **Обновите реестр и предложите действие.** Найдите компонент prompt/spec в `docs/harness-ledger.md`; обычно он связан со snapshot/variant, но не переносите вывод на всю инфраструктуру строки. Добавьте отдельную строку со свободным `LNNN`, если измеренное предположение иначе смешано с границей. Заполните компонент, предположение, ссылки на фактические baseline/without-spec records, дату/точную модель, retest trigger, ownership и статус. Правила реестра для «подтверждена» требуют реальные завершённые прогоны до/после; синтетического теста и этой инструкции недостаточно. Неизменный результат после удаления делает текст кандидатом на удаление, но не основанием снять Docker/network walls. Добавьте вывод в `experiments/<harness>/NOTES.md`.

   Решение о фактическом удалении оформляйте отдельным изменением с сохранением доказательств. При добавлении нового механизма вместо spec начинайте новую гипотезу и серию. Стоимость не ставьте 0 для красоты таблицы: local-only может обосновать нулевую inference fee, но не нулевую энергию, стоимость оборудования или неизвестное поле `cost_usd`.

## Что сдать

- Учебный report/manifest, заранее назначенные пары, measurements и raw compare JSON.
- Ссылки на шесть новых run records и независимые оценки; все отклонения и незавершённые состояния.
- Проверку равенства условий за исключением вмешательства, включая replay archive или seed commit.
- Ledger row/обновление с реальными evidence links и ограниченным выводом; заметку в NOTES.

## Критерии завершения

- [ ] Вмешательство ограничено штатным `without-spec`; task contract и границы сохранены.
- [ ] Три пары и порядок заданы заранее; каждая попытка имеет новый run ID.
- [ ] Остальные условия внутри пар совпадают либо различия явно лишают пару причинной интерпретации.
- [ ] Все исходы сохранены и независимо оценены, где исполнение дошло до review.
- [ ] Compare использует точные IDs; парный анализ выполнен отдельно от автоматической группировки.
- [ ] Реестр содержит реальные доказательства и триггер повторной проверки.
- [ ] Неизвестные метрики не заменены нулями; вывод не превышает объём серии.
- [ ] `npm run check` проходит; при незавершённой серии сдача помечена как неполная.

1. Почему удаление `inputs/spec.md` после prepare нарушит эксперимент?

3. Зачем нужен парный порядок, если модель всё равно недетерминирована?
4. Почему разные compare groups для baseline и ablation ожидаемы?
5. Можно ли сделать вывод о ненужности spec, если обе тройки состоят из fail?
6. Чем кандидат на удаление инструкции отличается от решения убрать инфраструктурную границу?
