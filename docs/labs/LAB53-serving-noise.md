# ЛР53. Шум сервинга и решения агента

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип работы | Двухуровневый контролируемый эксперимент: повтор записанных запросов агента на разных конфигурациях сервера, затем парная агентная серия |
| Время | Этап A: 2–3 часа оператора и около 3 часов машинного времени на минимум. Этап B: 20 попыток T002 по 15 минут, около 6 часов исполнения плюс независимая оценка |
| Предпосылки | ЛР08 (Linux-ветвь bridge, Pi/T002), ЛР04 (закреплённые backend), ЛР26 (driver и понимание server slots) |
| Готовность | `target-machine`; инструмент replay/analyze и его offline tests готовы. Этап B использует только Pi, единственную обвязку с допуском к локальному bridge |
| Минимальный объём | Этап A: 4 условия × 10 ходов × 5 повторов = 200 ответов. Этап B: 2 конфигурации × 10 попыток = 20 попыток |
| Расширение | Prefix cache, второй quant, vLLM BF16, полные 28 ходов; агентный опыт с соседней нагрузкой после доработки bridge |

## Цель

Измерить, сколько разброса в поведении агента создаёт слой сервинга сам по себе, при неизменных модели, обвязке, задаче и `temperature 0`. Разложить расхождения попыток на три источника: сервер (движок, backend, батч), обвязка и среда (run id, идентификаторы вызовов, время в выводе команд) и сэмплинг. Получить правило: сколько повторов нужно, чтобы различие двух локальных конфигураций что-то значило.

## Проверяемая гипотеза

Существующие записи уже показывают, почему вопрос не решается одним сравнением вердиктов. В `2026-10-12-pi-a2-janitor-t002-repo-janitor-4` и `-5` все условия сервера одинаковы, `temperature 0`, `seed 1`, но первый запрос различается run id: контракт T002 требует ветку `janitor/<run-id>`. Начиная со второго хода запросы расходятся ещё и по случайным ID вызовов инструментов, которые генерирует Pi, по времени в выводе `ls -la` и по тексту reasoning, который обвязка возвращает в историю. Поэтому расхождение двух агентных попыток нельзя приписать серверу без отдельного опыта, где вход побайтно одинаков.

До запусков запишите в `report.md` четыре гипотезы и правила их проверки:

- **H1, детерминизм базовой конфигурации.** На конфигурации S0 повтор побайтно одинакового запроса даёт побайтно одинаковый ответ. Опровергается любым различием reasoning, текста или вызова инструмента.
- **H2, соседи по батчу.** При четырёх слотах доля смены действия с тремя одновременными соседними запросами (S2b) выше, чем без соседей (S2a). Опровергается, если она не выше.
- **H3, масштаб.** Доля смены действия от серверного фактора (S2b, S3) сопоставима с долей от замены run id в промпте (якорь P1). «Сопоставима» означает не меньше половины доли P1. Это порог решения для малой выборки, не статистический тест.
- **H4, агентный уровень.** На S0 вердикты 10 попыток не все одинаковы. Различие S0 и выбранной конфигурации B1 считается найденным, только если двусторонний точный тест Фишера даёт p < 0,05. При 10 попытках на конфигурацию это требует разницы около 6 из 10 (8/10 против 2/10 даёт p = 0,023; 7/10 против 2/10 — p = 0,07). Отсутствие такого различия не доказывает эквивалентность.

«Действие» — то, что обвязка сделает следующим шагом: имя и аргументы вызова инструмента после разбора JSON, а если вызова нет, итоговый текст. Расхождение только в reasoning при одинаковом действии фиксируется отдельно и не считается сменой действия.

## Подготовка

```bash
npm run lab:new -- --lab LAB53 --session my-session
LAB_DIR='experiments/local-models/measurements/LAB53-my-session'
python3 -B docs/labs/fixtures/serving_noise_test.py
python3 -B docs/labs/fixtures/serving_noise.py replay --help
python3 -B docs/labs/fixtures/serving_noise.py analyze --help
npm run check
```

**Корпус запросов.** Этап A повторяет запросы из уже записанной попытки. По умолчанию используйте `results/runs/2026-10-15-pi-a2-janitor-t002-repo-janitor/trace/inference` (28 ходов, completed/pass). До запусков выберите 10 ходов по фиксированному правилу, например 1, 4, 7, …, 28, и запишите их в протокол. Подбор ходов после просмотра ответов запрещён. Запросы содержат вывод инструментов из учебного workspace T002 и не содержат секретов; корпус не меняется на протяжении всей работы.

**Базовая конфигурация S0** — deployment из ЛР08: `unsloth/Qwen3.5-9B-GGUF` @ `3885219b…`, `Qwen3.5-9B-Q6_K.gguf` (SHA-256 `91898433…`), llama.cpp `b8407` ROCm 7.2.1 на gfx1151, контекст 32768, `-np 1`, KV f16, batch 512, ubatch 256, threads 8, `-fa on`, `--jinja`, `--no-context-shift`, `--no-cache-prompt`, thinking on. Точную командную строку возьмите из `experiments/common/local-runtime.mjs` и `local-deployment.json` эталонной попытки, а не из этой методички. Проверьте SHA-256 весов и бинарника по ЛР03 до первой серии.

**Сервер этапа A** запускается вручную на loopback, как в ЛР26, потому что bridge ЛР08 сам управляет своим процессом и закрывает порт от внешних клиентов. Инструмент принимает только `http://127.0.0.1:PORT/v1/chat/completions` или `[::1]`, не передаёт авторизацию, не повторяет неудачные запросы и не исполняет вызовы инструментов из ответов. Перед каждым условием сохраните `GET /props` и лог запуска с подтверждением offload. Один сервер работает в один момент времени.

## Порядок выполнения

1. **Зарегистрируйте протокол.** До первого запроса закоммитьте `raw/protocol.md`: гипотезы H1–H4, корпус и номера ходов, список условий и порядок их выполнения, число повторов, правило выбора B1 (шаг 6), правило учёта сбоев. Технический сбой ответа остаётся в `results.jsonl` с текстом ошибки и не повторяется задним числом.

2. **Этап A, минимум: четыре условия.** Каждое условие пишет в новый каталог; повторный запуск с тем же `--out` будет отклонён.

   | Условие | Сервер | Параметры replay | Что изолирует |
   | --- | --- | --- | --- |
   | S0 | Как в ЛР08, `-np 1` | `--repeats 5 --order interleaved` | Повтор одинакового входа |
   | S2a | `-np 4`, контекст `-c 131072` (по 32768 на слот) | `--parallel 1` | Изменение конфигурации без нагрузки |
   | S2b | Тот же сервер, что S2a | `--parallel 4` | Три соседних запроса в одном батче |
   | P1 | Сервер S0 | `--substitute '<run id эталона>=<новый run id>'` | Якорь: изменение промпта на один идентификатор |

   Пример для S0:

   ```bash
   TRACE='results/runs/2026-10-15-pi-a2-janitor-t002-repo-janitor/trace/inference'
   TURNS='1,4,7,10,13,16,19,22,25,28'
   python3 -B docs/labs/fixtures/serving_noise.py replay \
     --endpoint 'http://127.0.0.1:18080/v1/chat/completions' \
     --trace "$TRACE" --turns "$TURNS" --repeats 5 --order interleaved \
     --condition S0 --out "$LAB_DIR/raw/replay-S0"
   ```

   Для P1 используйте реальный run id эталонной попытки как источник замены и новый run id того же формата. Если контекст `-c 131072` не проходит ресурсный допуск по ЛР02, уменьшите число слотов до 2 для S2a и S2b одновременно и запишите это отклонение. Ориентир по эталонной попытке: около 30 секунд на ход, то есть около 25 минут на условие S0.

3. **Этап A, расширения по желанию.** Каждое добавляется отдельной строкой протокола до запуска:

   - **S3, backend:** тот же GGUF на сборке llama.cpp b8407 Vulkan из ЛР04.
   - **S4, квантизация:** Q8_0 той же ревизии с подтверждённым происхождением по ЛР25.
   - **S1, prefix cache:** сервер без `--no-cache-prompt`, порядок `--order blocked` против `interleaved`. Семантику кэша в закреплённой сборке проверьте по `--help`; в этой методичке она не утверждается.
   - **S5, движок:** vLLM с BF16-чекпойнтом из ЛР06. Это сравнение двух deployments: меняются и веса, и движок.
   - **T1, якорь сэмплинга:** S0 с `--temperature`, равной рекомендованной в model card выбранной ревизии.
   - **Логиты:** `--top-logprobs 5` на S0 и S2b, если сборка возвращает logprobs в потоке. Тогда анализ показывает разрыв между двумя лучшими токенами в точке расхождения. Поддержка logprobs в b8407 — unverified до проверки.

4. **Проанализируйте этап A.** Два вида сравнения для каждого условия:

   ```bash
   # Внутри условия: эталон — первый ответ этого же условия
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$LAB_DIR/raw/replay-S2b" --out "$LAB_DIR/raw/analysis-S2b-self.json"
   # Против базовой конфигурации: эталон — первый ответ S0
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$LAB_DIR/raw/replay-S0" --source "$LAB_DIR/raw/replay-S2b" \
     --source "$LAB_DIR/raw/replay-P1" --out "$LAB_DIR/raw/analysis-vs-S0.json"
   ```

   Для каждого условия в таблицу переносятся: доля побайтно одинаковых ответов, доля смены действия, число ходов хотя бы с одной сменой, медиана позиции первого расхождения. Позиция считается в символах склейки reasoning и текста; при наличии logprobs дополнительно приводится разрыв в точке расхождения. Ответы сервера S2a сравниваются с S0, чтобы отделить эффект самой конфигурации слотов от эффекта соседей.

5. **Разложите расхождения существующих попыток.** Анализ трёх уже записанных попыток показывает, на каком ходу начинается расхождение и был ли вход в этот момент одинаковым:

   ```bash
   R='results/runs'
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$R/2026-10-12-pi-a2-janitor-t002-repo-janitor-4/trace/inference" \
     --source "$R/2026-10-12-pi-a2-janitor-t002-repo-janitor-5/trace/inference" \
     --out "$LAB_DIR/raw/analysis-existing-4-5.json"
   ```

   Поле `same_input_as_reference` сравнивает запросы после замены run id и идентификаторов вызовов на стабильные метки. Время в выводе команд и reasoning в истории не нормализуются: это и есть шум среды и обвязки. Для двух агентных попыток сравнимы только ходы до первого различия входа; дальше сравниваются уже разные ситуации.

6. **Выберите B1 по правилу из протокола.** Кандидаты — серверные факторы, которые bridge ЛР08 умеет запечатывать без доработки: S3 (backend) и S4 (quant), если они выполнены. B1 — кандидат с наибольшей долей смены действия против S0. Если ни один не выполнен, B1 = S3. Слоты и соседняя нагрузка на агентном уровне требуют доработки bridge: сейчас `local-runtime.mjs` запускает сервер с `-np 1`, а порт процесса недоступен для внешней нагрузки. Такое расширение — отдельная инженерная задача с собственной строкой реестра.

7. **Этап B: агентная серия.** 10 попыток S0 и 10 попыток B1 на T002 через `run --provider local`, порядок ABBA по парам: S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0. Контекст 32768 и timeout 1800 s, как в группе ЛР08, где попытки завершали исполнение. Один сервер за раз; смену deployment проверяйте по fingerprint в `run.json`. Каждая попытка получает чистый workspace и новый run id, `aborted` сохраняются. Команды подготовки и запуска скопируйте из отчёта ЛР08, а не из этой методички.

8. **Получите независимые вердикты.** Для каждой попытки в статусе `awaiting_review` используйте `evaluation-template` и `judge-run` по [общему workflow](harness-workflow.md). Оценщику передаются обезличенные результаты без метки конфигурации. `tasks/*/check/` агенту недоступны.

9. **Проанализируйте этап B.** Для каждой конфигурации: k/10 pass с 95% интервалом Уилсона, распределение `stop_reason` (`stop` против `max_turns`), ходы, токены и время. Для каждой пары попыток внутри конфигурации — ход первой смены действия и был ли вход на этом ходу одинаковым:

   ```bash
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "results/runs/<первая попытка S0>/trace/inference" \
     --source "results/runs/<вторая попытка S0>/trace/inference" \
     --out "$LAB_DIR/raw/analysis-B-S0-1-2.json"
   ```

   Сравнение групп выгрузите через `npm run --silent compare -- --runs <20 run id>`; S0 и B1 должны оказаться в разных группах по `local_inference`. Точный тест Фишера и интервалы посчитайте отдельным скриптом в `raw/` и приложите его.

10. **Сформулируйте ограниченный вывод.** Ответьте на H1–H4 по заранее записанным правилам. Главный практический результат — число повторов, начиная с которого разница между двумя конфигурациями на T002 различима для этой модели. Перенос на другие модели, задачи и движки не заявляется.

## Контрольные вопросы

1. Почему `temperature 0` и одинаковый `seed` не делают агентную попытку повторяемой, даже если сервер детерминирован?
2. Чем отличается смена reasoning от смены действия, и почему для агента важна вторая?
3. Почему после первого различия входа сравнение двух трасс по ходам теряет смысл?
4. Как число одновременно обслуживаемых запросов может изменить результат одного из них?
5. Что даёт якорь P1 для интерпретации доли смены действия от сервера?
6. Почему 10 попыток на конфигурацию не позволяют утверждать, что две конфигурации равноценны?
