# LAB53. Serving noise and agent decisions

## Profile

| Field | Value |
| --- | --- |
| Lab type | Two-level controlled experiment: replay recorded agent requests across server configurations, then run a paired agent series |
| Time | Stage A: 2–3 operator hours and about 3 machine hours for the minimum. Stage B: 20 T002 attempts of 15 minutes, about 6 execution hours plus independent evaluation |
| Prerequisites | LAB08 (Linux bridge branch, Pi/T002), LAB04 (pinned backends), LAB26 (driver and server-slot concepts) |
| Readiness | `target-machine`; replay/analyze tool and offline tests are ready. Stage B uses only Pi, the sole harness admitted to the local bridge |
| Minimum scope | Stage A: 4 conditions × 10 turns × 5 repetitions = 200 responses. Stage B: 2 configurations × 10 attempts = 20 attempts |
| Extension | Prefix cache, second quant, vLLM BF16, all 28 turns; agent experiment with neighboring load after bridge changes |

## Objective

Measure how much agent-behavior variability the serving layer alone produces with model, harness, task and `temperature 0` fixed. Separate attempt differences into three sources: server (engine, backend, batch), harness/environment (run ID, call IDs, command-output timestamps), and sampling. Derive a rule for how many repetitions are needed for a difference between two local configurations to mean something.

## Hypothesis

Existing records show why comparing verdicts alone cannot answer this. In `2026-10-12-pi-a2-janitor-t002-repo-janitor-4` and `-5`, server conditions are identical, with `temperature 0`, `seed 1`, but the first request differs by run ID: the T002 contract requires branch `janitor/<run-id>`. From the second turn, requests also differ through random tool-call IDs generated by Pi, timestamps in `ls -la` output, and reasoning text returned to history by the harness. Differences between two agent attempts therefore cannot be attributed to the server without a separate experiment using byte-identical input.

Before execution, record four hypotheses and their decision rules in `report.md`:

- **H1, baseline determinism.** On S0, repeating a byte-identical request yields a byte-identical response. Any difference in reasoning, text or tool call falsifies it.
- **H2, batch neighbors.** With four slots, the action-change rate with three concurrent neighboring requests (S2b) is higher than without neighbors (S2a). Falsified if it is not higher.
- **H3, magnitude.** The action-change rate from a server factor (S2b, S3) is comparable to the rate from replacing the prompt run ID (P1 anchor). “Comparable” means at least half the P1 rate. This is a small-sample decision threshold, not a statistical test.
- **H4, agent level.** On S0, the verdicts of 10 attempts are not all identical. A difference between S0 and the selected B1 configuration is established only if a two-sided Fisher exact test gives p < 0.05. With 10 attempts per configuration, this requires a difference of about 6 out of 10 (8/10 versus 2/10 gives p = 0.023; 7/10 versus 2/10 gives p = 0.07). Failure to find such a difference does not prove equivalence.

“Action” means what the harness will do next: tool-call name and arguments after JSON parsing, or final text if there is no call. A reasoning-only difference with the same action is recorded separately and does not count as an action change.

## Procedure

1. **Register the protocol.** Before the first request, commit `raw/protocol.md`: H1–H4, corpus and turn numbers, conditions and execution order, repetition count, B1 selection rule (step 6), failure-accounting rule. Technical response failures remain in `results.jsonl` with the error text and are not retrospectively retried.

2. **Stage A minimum: four conditions.** Each condition writes to a new directory; reuse of the same `--out` is rejected.

   | Condition | Server | Replay parameters | Isolates |
   | --- | --- | --- | --- |
   | S0 | As in LAB08, `-np 1` | `--repeats 5 --order interleaved` | Repetition of identical input |
   | S2a | `-np 4`, context `-c 131072` (32768 per slot) | `--parallel 1` | Configuration change without load |
   | S2b | Same server as S2a | `--parallel 4` | Three neighboring requests in one batch |
   | P1 | S0 server | `--substitute '<reference run id>=<new run id>'` | Anchor: one-identifier prompt change |

   S0 example:

   ```bash
   TRACE='results/runs/2026-10-15-pi-a2-janitor-t002-repo-janitor/trace/inference'
   TURNS='1,4,7,10,13,16,19,22,25,28'
   python3 -B docs/labs/fixtures/serving_noise.py replay \
     --endpoint 'http://127.0.0.1:18080/v1/chat/completions' \
     --trace "$TRACE" --turns "$TURNS" --repeats 5 --order interleaved \
     --condition S0 --out "$LAB_DIR/raw/replay-S0"
   ```

   For P1, use the actual reference attempt's run ID as the replacement source and a new run ID in the same format. If context `-c 131072` fails LAB02 resource admission, reduce slots to 2 for both S2a and S2b and record the deviation. Reference-attempt estimate: about 30 seconds per turn, or about 25 minutes for condition S0.

3. **Optional stage A extensions.** Add each as a separate protocol row before execution:

   - **S3, backend:** the same GGUF on the LAB04 llama.cpp b8407 Vulkan build.
   - **S4, quantization:** Q8_0 from the same revision with LAB25-confirmed provenance.
   - **S1, prefix cache:** server without `--no-cache-prompt`, `--order blocked` versus `interleaved`. Check cache semantics in the pinned build's `--help`; this manual makes no claim about them.
   - **S5, engine:** vLLM with the LAB06 BF16 checkpoint. This compares two deployments: both weights and engine change.
   - **T1, sampling anchor:** S0 with `--temperature` set to the recommendation in the selected revision's model card.
   - **Logits:** `--top-logprobs 5` on S0 and S2b if the build returns logprobs in the stream. Analysis then shows the gap between the two best tokens at divergence. Logprobs support in b8407 is unverified until checked.

4. **Analyze stage A.** Two comparisons per condition:

   ```bash
   # Within condition: reference is this condition's first response
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$LAB_DIR/raw/replay-S2b" --out "$LAB_DIR/raw/analysis-S2b-self.json"
   # Against baseline: reference is the first S0 response
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$LAB_DIR/raw/replay-S0" --source "$LAB_DIR/raw/replay-S2b" \
     --source "$LAB_DIR/raw/replay-P1" --out "$LAB_DIR/raw/analysis-vs-S0.json"
   ```

   For each condition, transfer to the table: fraction of byte-identical responses, action-change rate, turns with at least one change, median first-divergence position. Position is counted in characters of concatenated reasoning and text; when logprobs exist, also report the gap at divergence. Compare S2a server responses with S0 to separate the slot-configuration effect from the neighbor effect.

5. **Decompose differences in existing attempts.** Analysis of three recorded attempts shows the turn where divergence begins and whether input was identical then:

   ```bash
   R='results/runs'
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "$R/2026-10-12-pi-a2-janitor-t002-repo-janitor-4/trace/inference" \
     --source "$R/2026-10-12-pi-a2-janitor-t002-repo-janitor-5/trace/inference" \
     --out "$LAB_DIR/raw/analysis-existing-4-5.json"
   ```

   `same_input_as_reference` compares requests after replacing run IDs and call IDs with stable labels. Command-output timestamps and reasoning in history are not normalized: these are environment/harness noise. For two agent attempts, only turns before the first input difference are comparable; afterward they represent different situations.

6. **Select B1 using the protocol rule.** Candidates are server factors that the LAB08 bridge can seal without changes: S3 (backend) and S4 (quant), if run. B1 is the candidate with the highest action-change rate against S0. If neither was run, B1 = S3. Agent-level slots and neighboring load require bridge changes: `local-runtime.mjs` currently starts the server with `-np 1`, and the process port is inaccessible to external load. This extension is a separate engineering task with its own ledger row.

7. **Stage B: agent series.** Ten S0 and ten B1 attempts on T002 through `run --provider local`, paired ABBA order: S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0, S0, B1, B1, S0. Context 32768 and timeout 1800 s, as in the LAB08 group whose attempts completed execution. One server at a time; check deployment changes via the `run.json` fingerprint. Every attempt gets a clean workspace and new run ID; preserve `aborted` attempts. Copy preparation/execution commands from the LAB08 report, not this manual.

8. **Obtain independent verdicts.** For each `awaiting_review` attempt, use `evaluation-template` and `judge-run` according to the [shared workflow](harness-workflow.md). Give the evaluator anonymized results without configuration labels. The agent cannot access `tasks/*/check/`.

9. **Analyze stage B.** Per configuration: k/10 pass with 95% Wilson interval, `stop_reason` distribution (`stop` versus `max_turns`), turns, tokens and time. For every within-configuration attempt pair: turn of first action change and whether input was identical at that turn:

   ```bash
   python3 -B docs/labs/fixtures/serving_noise.py analyze \
     --source "results/runs/<first S0 attempt>/trace/inference" \
     --source "results/runs/<second S0 attempt>/trace/inference" \
     --out "$LAB_DIR/raw/analysis-B-S0-1-2.json"
   ```

   Export the group comparison through `npm run --silent compare -- --runs <20 run id>`; S0 and B1 must fall into different `local_inference` groups. Calculate Fisher's exact test and intervals in a separate script in `raw/` and attach it.

10. **State a bounded conclusion.** Answer H1–H4 under the preregistered rules. The main practical result is the repetition count at which two configurations become distinguishable on T002 for this model. Make no claim of transfer to other models, tasks or engines.

## Review questions

1. Why do `temperature 0` and the same `seed` not make an agent attempt reproducible, even with a deterministic server?
2. How does a reasoning change differ from an action change, and why does the latter matter for an agent?
3. Why does turn-by-turn comparison of two traces cease to be meaningful after the first input difference?
4. How can the number of concurrently served requests change the result of one of them?
5. How does the P1 anchor help interpret the server-induced action-change rate?
6. Why do 10 attempts per configuration not establish that two configurations are equivalent?
