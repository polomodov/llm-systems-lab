## Цель

Построить первый слой поверх платформы: сервер инструментов, через который любая обвязка исполняет код в SPACE, и проверить, хватает ли узкого интерфейса для реальной задачи. Это схема, обратная [ЛР37](LAB37-space-harness-vm.md): там агент живёт в VM, здесь в VM уходят только его действия.

## Проверяемая гипотеза

Четырёх инструментов — `run_command`, `read_file`, `write_file`, `list_dir` — поверх native API SPACE достаточно, чтобы обе выбранные обвязки решили T002 с тем же verdict, что в Docker-пилоте, без встроенных shell/file-инструментов. Медиана накладных расходов SPACE на один `run_command` (create session → `process_exited` для `true`) не превышает порог, который вы фиксируете в протоколе до замера.

## Подготовка

- Образец клиента — `examples/llm_agent.py` из чернового PR polomodov/SPACE#1: command session, проверка `events_url`, SSE, base64-кадры, `process_exited`, удаление песочницы в `finally`.
- Транспорт к обвязке: MCP для обвязок, где он поддержан закреплённой версией (Claude Code; OpenHands SDK — проверить по документации 1.49.2), либо native custom tools SDK (Pi — проверить по `docs/sdk.md` тега v0.73.1). Поддержка, не подтверждённая документацией закреплённой версии, — `unverified`.
- Выбор двух обвязок и порог накладных расходов записываются в `raw/protocol.md` до первого прогона.

```bash
npm run lab:new -- --lab LAB38 --session ryzen-01
LAB_DIR='experiments/space/measurements/LAB38-ryzen-01'
```

## Порядок выполнения

1. **Контракт инструментов.** Опишите в `experiments/space/tools/README.md` схему каждого инструмента: входы, лимиты (timeout команды, размер вывода, обрезка посередине), формат ошибки, что сохраняется между вызовами (файлы — да, shell-состояние — нет). Одна песочница на эпизод; её ID видит только сервер.

2. **Реализация.** Сервер создаёт песочницу при старте эпизода и удаляет при завершении, логирует каждый вызов (инструмент, длительность, код выхода, размер вывода) в JSONL. Токен SPACE передаётся серверу через окружение раннера и в агентский контекст не попадает.

3. **Офлайн-тесты.** Фейковый control/data plane (как в тестах PR SPACE): ненулевой код — результат, а не ошибка; обрыв SSE без `process_exited` — ошибка; чужой `events_url` не получает токен; удаление песочницы после сбоя.

4. **Подключение к обвязкам.** Для каждой выбранной обвязки — вариант профиля, где встроенные shell/file-инструменты отключены, а подключён сервер. Изменение профиля — строка ledger.

5. **Замер накладных расходов.** 30 вызовов `run_command('true')` и 30 вызовов `write_file`+`read_file` на 4 KiB; сырые длительности в `measurements.tsv`.

6. **Эпизоды T002.** По одной попытке на обвязку через полный цикл `new-run → prepare-run → run → judge-run`. Сравните с Docker-пилотом этой обвязки.

7. **Расширение: ECW.** Тот же сценарий через `e2b-code-interpreter` с адресом SPACE ECW. Запишите, какие методы SDK отвечают 501 или ведут себя иначе.

## Критерии завершения

- Офлайн-тесты сервера проходят в `npm test`; `npm run check` проходит.
- Обе обвязки выполнили T002 с отключёнными встроенными инструментами; verdict независимый.
- Накладные расходы измерены по сырым данным, гипотеза о пороге принята или отвергнута.
- Токен SPACE не встречается в трассах агента.
