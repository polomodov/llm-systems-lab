# ЛР08. Локальный provider bridge и воспроизводимая запись инференса

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип работы | Инженерная: спроектировать, реализовать и проверить интеграцию; это не только запуск измерений |
| Время | Ориентир 12–20 часов разработки и проверки после готовности сервера; время устранения несовместимости SDK учитывается отдельно |
| Предпосылки | ЛР01 и одна из ЛР05 (Ryzen/Linux) или ЛР32 (Apple/macOS); паспорт машины, закреплённые веса и рабочий protocol smoke |
| Готовность | Pi/T002 bridge и metadata реализованы для native llama.cpp Metal/macOS и ROCm/Linux. [Ryzen pilot](https://github.com/polomodov/agent-harnesses-exps/blob/1624dc86491cb3a1f7ab66d78fba0b498e14ef1b/experiments/local-models/measurements/LAB08-ryzen-linux-bridge/report.md) имеет независимые verdict, но сводный отчёт blocked по предрегистрации; [Apple pilot](https://github.com/polomodov/agent-harnesses-exps/blob/1624dc86491cb3a1f7ab66d78fba0b498e14ef1b/experiments/local-models/measurements/LAB08-apple-native-requalification-20261010/report.md) ждёт оценки. Остальные adapters **pending** |
| Минимальный объём | Один backend, одна модель, один адаптер Pi или mini-SWE-agent, синтетическая матрица и один реальный T002 pilot |
| Расширение | Подключение остальных основных локальных обвязок: Pi, mini-SWE-agent, OpenCode, OpenHands |

## Цель

Соединить изолированный agent container с доверенным локальным inference service, сохранив запрет доступа к остальной сети и воспроизводимость эксперимента. Запись должна различать одинаковый model alias с разными весами, движком, контекстом и настройками.

## Проверяемая гипотеза

Отдельный маршрут к одному inference endpoint позволяет выполнить штатный цикл инструментов выбранной обвязки без расширения сетевых прав агента. При смене существенного условия инференса координатор либо отказывается запускать запечатанную конфигурацию, либо создаёт новую группу сравнения; такая смена не маскируется прежним model alias.

Критерий опровержения: доступ к другому адресу/порту, административному API или облачному fallback; потерянный tool-result; попадание двух разных конфигураций весов в одну группу; выдача отсутствующего usage за нулевой.

## Подготовка

Для Apple inference server работает нативно в macOS; контейнер содержит только agent harness. Подключение из Docker Desktop к host endpoint требуется спроектировать и проверить отдельно: `127.0.0.1` контейнера не является loopback Mac, а имя `host.docker.internal` само по себе не обеспечивает изоляцию. Bridge должен разрешать только закреплённый endpoint и пройти ту же матрицу B01–B10. Не публикуйте server в LAN как замену этой проверки. MLX server alias и MLX artifact manifest требуют того же контроля identity, что GGUF. Пока bridge не принят, Apple-agent серии остаются `pending/blocked`.

Создайте папку учебной работы из корня репозитория:

```bash
npm run lab:new -- --lab LAB08 --session my-session
LAB_DIR='experiments/local-models/measurements/LAB08-my-session'
npm run harnesses
npm test
npm run check
```

Выберите каталог своего стенда; автоматического выбора по машине нет:

```bash
# Вход через ЛР05: Ryzen / Linux
npm run local:engines -- --hardware ryzen-ai-max-395-128gb-linux
# Вход через ЛР32: Apple / macOS
npm run local:engines -- --hardware apple-m5-max-128gb-macos
```

В отчёте укажите выбранный hardware ID и ссылку на допущенное условие protocol smoke: ЛР05 для Ryzen либо ЛР32 для Apple. Частичный допуск контекста не распространяется на другие контексты или настройки reasoning.

`report.md`, `measurements.tsv`, черновой `manifest.json` и `raw/` относятся к учебной работе. Реальная агентная попытка получает отдельный `results/runs/<run-id>/run.json`. Учебный отчёт не заменяет его.

Прочитайте `scripts/lib/harnesses.mjs`, `scripts/prepare-run.mjs`, `scripts/run.mjs`, `experiments/common/egress.mjs`, `results/schema.json`, `scripts/lib/records.mjs` и `scripts/compare.mjs`. Скрытые проверки не открывайте, контракты `tasks/*/task.md` не изменяйте. Подготовьте одну доступную модель из ЛР05 (Ryzen) либо ЛР32 (Apple) с закреплёнными артефактами и прошедшими chat/tool/cancel/overflow/recovery именно для выбранного deployment; сервер без встроенных shell/tools и без mount исходного репозитория лаборатории.

## Порядок выполнения

1. **Опишите исходное ограничение и текущую реализацию.** В отчёте приведите ссылки на проверенный Git commit и места кода: облачный профиль содержит `connect_domains`, CONNECT разрешает закреплённые домены на 443, публичный resolver отклоняет private/reserved IP. Local provider использует отдельный bridge и версионированный `local_inference` fingerprint. Запишите выбранную модель, обвязку и сервер. Интерфейс `prepare-run --provider local --local-deployment ...` и `run --provider local` описан в [Pi README](../../experiments/pi/README.md); он ограничен Pi/T002 и controlled native llama.cpp на Metal/macOS или ROCm/Linux, стартует собственный pinned server. Не обходите эту границу, подставляя LAN-адрес вместо облачного домена.

2. **Зафиксируйте контракт интеграции до кода.** В `report.md` опишите конфигурацию endpoint: доверенный адрес, порт, транспорт, разрешённые методы/пути, identity alias, границы request/response и timeout. Выберите минимальный API для конкретного адаптера; например, chat completions не означает автоматического разрешения всего `/v1/`. Проверка доступности должна быть отдельным разрешённым маршрутом. Задайте поведение для redirect, streaming disconnect, смены адреса и неизвестной модели. Нужен отказ с диагностикой, а не переключение на другую модель или облако.

3. **Спроектируйте границу сети.** Model server работает вне 2 GiB task container, доступен только доверенному bridge. Agent container сохраняет собственный изолированный Docker network, workspace mounts, непривилегированного пользователя и внешний timeout. Bridge пересылает запрос только на зафиксированный endpoint; агент не передаёт произвольный target URL или Host для выбора upstream. Не разрешайте всю LAN, host networking, Docker socket, административные маршруты сервера или прямой доступ к устройствам из task container. Существующий GET gateway источников T001 и его публичный SSRF-фильтр сохраняются.

4. **Добавьте минимальный профиль провайдера и адаптер.** Реализуйте отдельный local policy в validator, prepare snapshot, gateway и одном выбранном адаптере. Используйте собственный agent loop Pi/mini-SWE-agent; не заменяйте его общим циклом. Для Pi проверьте streaming tool-call → tool-result → final; для mini-SWE-agent — также штатный текстовый action protocol. Зафиксируйте context/output limits, chat template и reasoning/sampling. Если сервер требует секрет, его источник — `.env` и выбранный профиль; не включайте значение в snapshot, manifest или лог. Отдельно документируйте, нужен ли dummy auth marker.

5. **Расширьте данные, а не только URL.** Спроектируйте и реализуйте версионированные поля схемы, их валидацию и неизменность после prepare. Приведённые ниже названия — требования к данным, не существующие поля `run.json`. Не добавляйте их вручную в старые записи.

   | Группа данных | Обязательное содержание |
   | --- | --- |
   | Идентичность модели | Официальный repository и revision; точные файлы, bytes и проверенные SHA-256; quant/format; requested alias и наблюдаемая identity с основанием |
   | Движок | Engine/version/commit, GPU backend Vulkan, ROCm или Metal, build flags, serving wrapper/version, image digest при контейнерном запуске |
   | Входной протокол | Hash tokenizer/chat template; context/output budgets; sampling, seed если поддержан, reasoning; формат tools/action protocol |
   | Память и исполнение | KV/state dtype, batch/ubatch, offload/GPU layers, slot count; hash аппаратного паспорта, driver и режим питания |
   | Происхождение | Запечатанный deployment manifest и его hash; подтверждение фактически запущенной конфигурации, отсутствие cloud fallback |
   | Метрики | Измеренные значения и единицы; отдельные причины для неизвестных токенов, памяти, энергии и стоимости |

6. **Подключите данные к prepare/run/compare.** Prepare сохраняет конфигурацию и fingerprint. Run проверяет соответствие сервера закреплённой конфигурации до агентного старта и обрабатывает обнаруженную смену identity во время запуска. Один ответ `/models` с тем же alias не доказывает сохранение весов: нужен проверяемый deployment manifest или эквивалентное свидетельство контролируемого процесса. Compare включает существенные поля в ключ условий, сохраняя различие cloud/local и engine/backend. Для GGUF и safetensors с разными квантизациями сравнивается deployment целиком, а не чистый эффект движка. Старые облачные записи продолжают валидироваться.

7. **Выполните синтетические acceptance tests.** Создайте mock inference server и тестовые ответы без настоящих ключей и скрытых задач. Каждому случаю дайте test ID, ожидаемый результат и ссылку на raw output. Минимальная матрица:

   | ID | Воздействие | Критерий приёмки |
   | --- | --- | --- |
   | B01 | Разрешённый запрос и штатный tool/action round-trip | Финальный ответ получен, события и tool-result сохранены без потери |
   | B02 | Тот же host, другой порт; другой LAN IP; IPv6-адрес вне разрешения | Отказ до соединения с запрещённым upstream; проверено счётчиком mock server |
   | B03 | Подмена Host/target, redirect, административный путь | Нет перехода к другому назначению и выполнения административного действия |
   | B04 | Обращение к cloud endpoint после локальной ошибки | Отказ; ни одного вызова облачного mock endpoint |
   | B05 | Слишком большой ответ, невалидный JSON, 4xx/5xx, оборванный stream | Ограниченный объём лога, явная ошибка; exit 0 клиента не превращает ошибку в успех |
   | B06 | Timeout и отмена | Agent container и временные ресурсы убраны; процесс общего model server не убит без отдельной причины |
   | B07 | Тот же alias, другие веса/template/context/backend | Запуск отвергнут или создано отдельное условие; данные не объединяются прежним alias |
   | B08 | Usage отсутствует | `null` с причиной; стоимость и токены не становятся 0 |
   | B09 | Изменение запечатанного manifest, секрет в trace/artifact | Integrity отказ или предусмотренная защита; значение секрета не попало в архив |
   | B10 | Старый cloud run и T001 replay | Обратная совместимость; private-source URL остаётся запрещён, live fallback в replay отсутствует |

8. **Проверьте интеграцию в Docker.** После unit tests выполните реальные проверки сетевой изоляции с mock endpoints. Сохраните stdout/stderr и параметры mock server в `raw/`. Выполните штатные проверки:

   ```bash
   npm test
   npm run test:docker
   npm run check
   git diff --check
   ```

   Дополнительные команды новых тестов запишите точно так, как они реализованы. Не отмечайте B01–B10 пройденными только по наличию тестового файла.

9. **Документируйте работающий CLI и проведите один pilot.** Только после реализации и предыдущих проверок добавьте в README адаптера точную команду с реально поддерживаемыми параметрами. Выполните один T002 с `a2-janitor` по жизненному циклу из ЛР09 и независимой оценкой. Запишите настоящий run ID; ошибки запуска тоже сохраняйте. Если инженерная часть не завершена, сдайте отчёт с `pending/blocked`, причиной и последним воспроизводимым тестом; не оформляйте фиктивный `completed`.

10. **Внесите компоненты в реестр.** Для каждой добавленной границы или адаптации добавьте свободный ID в `docs/harness-ledger.md` в том же изменении: компонент → предположение/граница → фактические тесты/run ID → дата/модель → retest trigger → ownership → статус. Факт работающего bridge ещё не доказывает его вклад в качество агента; статус «подтверждена» требует измерений до/после по правилам реестра. Перенос на остальные три адаптера оформите отдельными строками готовности и повторите protocol tests.

- `report.md`, `measurements.tsv`, заполненный manifest учебной сессии и raw logs.

## Критерии завершения

- [ ] Один выбранный адаптер использует свой штатный цикл через локальный bridge.
- [ ] B01–B10 проверены; forbidden destinations и cloud fallback действительно недоступны.
- [ ] Manifest и compare различают веса, template, backend и настройки с одинаковым alias.
- [ ] Метрики без наблюдений остаются неизвестными; старые cloud records валидны.
- [ ] Инженерные проверки и `npm run check` проходят.
- [ ] Есть один реальный pilot с независимой оценкой; незавершённая интеграция сдана как промежуточный отчёт, а не завершённая ЛР08.
- [ ] Новые компоненты записаны в реестр; готовность остальных адаптеров не приписана автоматически.

3. Почему серверу модели нельзя наследовать 2 GiB лимит task container?
