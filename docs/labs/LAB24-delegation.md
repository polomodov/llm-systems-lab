# ЛР24. Один агент и делегирование при общем бюджете

## Паспорт

| Поле | Значение |
| --- | --- |
| Тип | Инженерная интеграция orchestration и контролируемый эксперимент |
| Время | 4–8 часов подготовки/проверки; затем 6 попыток и независимый judge |
| Предпосылки | ЛР09; подходящий многошаговый эпизод; наблюдаемое исполнение всех участников |
| Готовность | `implementation-required`: универсального team-mode и суммарного бюджета в текущем runner нет |
| Минимальный объём | Одна модель/обвязка/задача × single/team × три пары = 6 попыток |
| Расширение | Второй эпизод; затем отдельное сравнение ролей или числа участников |

## Цель

Проверить, улучшает ли делегирование выполнение задачи после учёта всех затрат на планирование, передачу контекста, работу исполнителей и объединение правок. Выяснить, где параллельность помогает, а где создаёт повторную работу и конфликты.

## Проверяемая гипотеза

«Координатор с двумя исполнителями повышает успешность либо сокращает полное время без ухудшения успешности в пределах такого же суммарного бюджета, как один агент». Фактор — схема исполнения. Одинаковы исходная задача, модель всех участников, права, совокупный лимит ресурсов, judge и условия запуска.

До серии выберите основной критерий: качество (больше pass при общем лимите) **или** время (не меньше pass и меньшая медиана wall-clock среди полных успешных пар). Все три парных значения показываются независимо от основного критерия. Переключаться на удобный показатель после результатов нельзя. Три пары дают пилотный вывод; одна быстрая успешная команда не доказывает преимущество на других задачах.

## Подготовка

```bash
npm run lab:new -- --lab LAB24 --session team-pilot
LAB_DIR='experiments/local-models/measurements/LAB24-team-pilot'
npm run check
```

Подходит [миграция API и потребителя](episodes/interface-migration/episode.md): в ней есть связанные области работы и реальная точка объединения. Сначала выполните исходные открытые проверки на копии по [инструкции](episodes/README.md). Этот публичный fixture требует отдельной регистрации нового task ID для настоящих runs. Не заменяйте им содержимое существующей T002.

Проверьте возможности выбранной точной версии harness: native subagents, модель каждого участника, учёт usage, доступность traces, управление workspace и завершение дочерних процессов. Если функция не подтверждена исходниками или воспроизводимым smoke, укажите `unverified`. Реализация orchestration поверх SDK возможна как инженерное расширение; она становится частью исследуемой обвязки и получает ledger row.

## Порядок выполнения

1. **Задайте две стратегии.** Single — один агент выполняет весь контракт. Team — один координатор и максимум два исполнителя; координатор выбирает ограниченные поручения, принимает результаты и формирует итог. Всем назначается один точный model ID и одинаковые sampling/reasoning. Использование более дешёвой/сильной модели для одной роли — дополнительный фактор, допустимый только в следующей серии.

2. **Зафиксируйте права и пространство файлов.** Разрешённые действия и сеть одинаковы в двух режимах. Для команды выберите заранее один режим: изолированные рабочие копии с последующим merge либо общий workspace с непересекающимися назначенными файлами. В минимуме предпочтительны отдельные копии от одного seed и явное объединение координатором. Время копирования, merge, проверок и исправления конфликтов входит в wall-clock. Нельзя давать команде скрытый готовый план разделения, которого нет у single: если координатор получает подсказку, тот же содержательный план получает и single либо опыт называется сравнением всего workflow.

3. **Реализуйте общий ограничитель.** Один run имеет общий token cap B и deadline T. В B включаются все входы и выходы координатора и исполнителей, повторно переданный контекст, ошибки, retries и промежуточные сводки. Перед каждым model request диспетчер резервирует доступную часть бюджета; после ответа сверяет usage и освобождает остаток. При параллельных запросах нельзя позволить каждому участнику независимо потратить весь B. Если провайдер не позволяет заранее оценить/ограничить usage, фиксируйте это как observed budget и не называйте опыт сравнением при жёстком cap.

4. **Уравняйте доступные вычислительные ресурсы.** Совокупные CPU/RAM agent containers в team не должны незаметно утроиться; задайте общий предел или явно отметьте ресурсный конфаундер. Model server остаётся внешним. Для local укажите slots/concurrency, KV budget и очередь, проверенные в ЛР26; команда не получает другой deployment. Для cloud поставщик управляет внутренней очередью, поэтому wall-clock отражает наблюдаемый сервис в данной серии, а не чистую скорость вычислений. Денежный бюджет отдельно фиксируется там, где он наблюдаем; одинаковые tokens не означают одинаковую стоимость разных моделей.

5. **Соберите инженерный допуск runner.** Новый orchestration mode, role prompts/hash, общий бюджет, workspace policy и model IDs входят в sealed controls и условия compare. Trace содержит parent/child IDs, время создания/завершения, поручение, usage, изменения файлов и merge events; одна общая run record представляет итог задачи. Дочерние сессии хранятся как её trace, а не как независимые повторы успеха. Текущий CLI таких team-параметров не предоставляет; команды серии появятся в реализованном расширении. Новому эпизоду нужны seed, контракт и внешний judge.

6. **Проверьте orchestration на synthetic workers.** Два одновременно запрашивающих worker не превышают общий budget; ошибка одного сохраняется и видна координатору; deadline прекращает всю process tree; конфликтующий patch не молча затирает другой; trace и usage сохраняются при abort. Проверяйте и отказ до старта child, и отказ после частичного изменения. Никакие настоящие ключи или внешние сообщения для smoke не нужны. Если невозможно наблюдать native child usage, интеграция недостаточна для заявленного сравнения бюджета.

7. **Назначьте и исполните три пары.** Порядок single → team, team → single, single → team. Каждый вариант начинается с нового чистого seed; нельзя продолжать успешные правки single внутри team. Протокол, task ID, B/T, model/deployment, максимальное число участников и критерий выбора из гипотезы записаны до старта. Каждый режим получает новый run ID. Пилоты отладки исключены из сравнительной серии по предварительному правилу и сохранены отдельно. Local дополнительно требует завершённой ЛР08.

8. **Оцените общий результат.** Независимый judge видит итоговый workspace/артефакты без метки single/team. Отдельно разметьте дублирование исследований, несовместимые предположения об интерфейсе, конфликты правок, недостающие передачи информации и возврат работы координатору. Не считайте число созданных subagents показателем качества. Успешная часть одного worker не равна pass общей задачи.

9. **Сравните полный путь.** Покажите verdict, суммарные input/output, wall-clock от старта до итогового результата, максимальную фактическую параллельность, количество workers, время merge/rework и долю координационных токенов. Определите последнюю до разметки: например, сообщения назначения/отчёта/объединения; спорные сообщения оставьте неразмеченными. Сумма worker wall-times может превышать общее elapsed и не является latency. Не удаляйте из анализа team-abort или неудачный merge.

10. **Примите ограниченное решение.** Сначала примените заранее выбранный основной критерий, затем перечислите компромиссы. Если team быстрее только при большем фактическом бюджете, равенство условий нарушено; нужны исправление механизма и новая серия. При отсутствии эффекта проверьте, были ли части задачи независимо выполнимы и сколько времени ушло на координацию. Любое изменение ролей/разделения работ относится к новому эксперименту, а не к исправлению итоговой таблицы.

## Что сдать

Инженерную реализацию и budget/cleanup/merge tests, зарегистрированный эпизод, протокол трёх пар, полный общий и дочерние traces, шесть run records с независимыми оценками, таблицы времени/usage/координации и вывод. Если доступны только проект и ручное упражнение, пометьте измерительную часть `not-run`; файл отчёта не подтверждает работающий team-mode. Формат — [report-validation.md](report-validation.md).

## Критерии завершения

- [ ] Общий бюджет и deadline исполняются на уровне всей команды, а не каждого участника отдельно.
- [ ] Модели, права и вычислительные условия сопоставимы; дополнительные инструкции раскрыты.
- [ ] Запечатаны роли, workspace policy и условия группировки.
- [ ] Synthetic tests подтверждают budget, cleanup и обработку конфликтов.
- [ ] Все три пары независимо исполнены и оценены; child сессии не названы независимыми task runs.
- [ ] В затраты включены координация, retries, merge и rework; нет неучтённого usage.
- [ ] Вывод следует заранее выбранному критерию; `npm run check` проходит.

## Контрольные вопросы

1. Почему по B токенов каждому из трёх агентов не равно общему бюджету B?
2. Когда делегирование меняет не только параллельность, но и объём доступной информации?
3. Почему сумма времени workers отличается от wall-clock задачи?
4. Как учитывать частично успешного worker при неудачном итоговом merge?
5. Что можно заключить при хороших итогах, но неизвестном usage дочерних сессий?
