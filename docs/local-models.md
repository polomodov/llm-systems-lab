# Исследование локальных моделей

Пошаговое выполнение оформлено в [локальный маршрут ЛР01–10](labs/README.md); тот же практикум содержит отдельные ЛР11–19 по всем обвязкам и дополнительные ЛР20–27. Для Ryzen следующие измерения — [качество при разной квантизации](labs/LAB25-quantization-quality.md) после локального подключения и [параллельная нагрузка](labs/LAB26-concurrent-load.md) на работающем сервере. Ниже — исследовательский план расширенных серий; минимальный объём каждой лабораторной указан в её задании.

План от **20.09.2026**, расширен **21.09.2026** на разные движки инференса, для указанного владельцем **Ryzen AI Max+ 395, 128 GB общей памяти, Linux**. Цель — найти практичные локальные модели для наших автономных агентов, затем измерить, что требуется каждой обвязке с одной и той же моделью. Скорость генерации сама по себе не определяет качество агента.

Подготовлены [каталог кандидатов](local-model-candidates.md), [Linux runbook](local-model-runtime.md) и команда `npm run local:plan`. Модели на этой машине ещё не запускались. Размеры файлов и заявления разработчиков отделены от наших оценок; измеренных tokens/s, успешности задач и энергопотребления пока нет.

**Vulkan и HIP/ROCm — равноправные обязательные ветви.** [Матрица движков](local-inference-engines.md) добавляет vLLM, SGLang, Transformers/PyTorch, Ollama, LM Studio и Lemonade; последующие пункты этого плана учитывают расширение. Сервис поверх llama.cpp и независимый kernel engine сравниваются раздельно. Каталог GGUF не задаёт вес native checkpoint другого движка.

## Память и смысл «помещается»

128 GB — общая память CPU и GPU, её нельзя складывать с выделением GPU. Вендор описывает до 96 GB для графики, но это не измеренный Linux heap конкретной машины. До preflight используем консервативные **119,2 GiB общей памяти**, **89,4 GiB GPU budget**, **16 GiB резерва ОС/обвязки**. Единицы в planner — GiB (2³⁰ байт); 128/96 GB трактуются как десятичные для первоначальной нижней оценки. После проверки `/proc/meminfo` и Vulkan/ROCm эти предположения заменяются фактическими значениями. Источники и ограничения — в [hardware.json](../experiments/local-models/hardware.json) и runbook.

Расчёт очереди:

```text
budget = min(usable_RAM_GiB − OS_reserve_GiB, safe_GPU_budget_GiB)
estimate = weights_GiB + runtime_reserve_GiB + KV_or_state_reserve_GiB
headroom = budget − estimate
```

Runtime reserve сначала 6 GiB; KV/state reserve — 4/8/16 GiB для контекста 8/16/32K. Это **эвристика очереди**, не формула конкретной архитектуры. Dense attention, sliding window, MLA и гибридная recurrent state требуют разных расчётов. Веса MoE оцениваются по всем экспертам, а не по числу активных параметров. Необходимо отдельно проверить пиковую загрузку, prefill и generation: размер GGUF на диске недостаточен.

Кандидат допускается к серии, если загрузка и заполнение выбранного контекста завершаются без OOM, выхода за бюджет и постоянного swap-in/out. Остаётся оговорённый резерв ОС; доступность всех нужных GPU allocations подтверждена журналом. CPU offload, mmap и частичный GPU offload допустимы только как отдельный вариант с явными условиями, а не как незаметное спасение основной конфигурации.

## Порядок и объём кампании

Это последовательность рабочих сессий, а не обещание даты завершения. Обработка на машине строго последовательная: один model server, один slot, одна агентная попытка. Каталог сортируется по приоритету и затем размеру весов; большие условные кандидаты проверяются после малого контроля. Полная загрузка всех весов заранее не нужна: скачивать последовательно закреплённые артефакты, проверить свободный SSD с учётом временного кеша загрузчика.

| Этап | Что выполняется | Объём / предел | Условие перехода |
| --- | --- | --- | --- |
| 0. Паспорт машины | CPU, BIOS, Linux/kernel, RAM, GPU heap, Vulkan/ROCm, режим питания, SSD | Одна сессия; ориентир 1–2 часа без установки драйверов | Зафиксированы измеренные бюджеты, версии и исходное состояние |
| 1. Backend и протокол | Малый контроль; pinned llama.cpp Vulkan **и HIP/ROCm** на одном commit/артефакте; streaming, tools, reasoning | Ориентир 2–4 часа после готовности стека; incompatibility записывается, ветвь не исчезает молча | Валидные ответы и tool round-trip, нет скрытой подмены backend/model |
| 2. Отбор по ресурсам | Все кандидаты: 8K → 16K → 32K на обоих llama.cpp backend; затем самостоятельные ROCm engines и serving layers по матрице | До **216** baseline наборов (12 × 2 × 3 × 3); дополнительные ограниченные серии описаны в матрице, а не полное декартово произведение | На 16K стабильно помещается; 32K и каждый новый движок оцениваются отдельно |
| 3. Агентный pilot | Каждая прошедшая модель на A2/T002 в одной reference-обвязке Pi | По 1 новой попытке, timeout 900 секунд; 15 минут — лимит, не прогноз скорости | Получены trace и независимый verdict, зафиксированы все сбои |
| 3b. Влияние движка | До 3 финалистов × 2 прошедших engine deployments × T001/T002 × 3 повтора в Pi | До **36** новых попыток, до **9 часов** по timeout, отдельно от основной серии | Артефакты и quant учтены; сравнение разных quant трактуется как сравнение deployments |
| 4. Основная серия | До 3 финалистов × 4 обвязки × T001/T002 × 3 повтора | До **72** агентных попыток, до **18 часов** только на их timeout; плюс setup/evaluation | Сравнимые условия и полные тройки без отбора удачных |
| 5. Аудит и абляции | T003 для тех же 3 × 4 × 3; затем одна абляция у лучшей пары | До **36** аудитов (9 часов лимитов); первая абляция T002 — 3 дополнительных попытки | Аудит трактуется отдельно, эффект компонента — только до/после |

Этапы 0–2 можно проводить до интеграции агента. **Этапы 3–5, включая 3b, зависят от реализации local-provider bridge и расширения записи результатов**, описанных ниже. Запускать их существующими облачными профилями, отключив ограничения сети, нельзя. До основной серии выбрать и закрепить один engine deployment на модель; затем его не менять между четырьмя обвязками.

Лимит 900 секунд единый для сравниваемых агентных конфигураций; лимиты ходов и контрактов задач сохраняются. Если лучшие локальные модели систематически упираются во время, до новой серии объявить отдельную группу с 1800 секундами для всех участников, не продлевать отдельные неудачные попытки. Абляции Q4/Q6/Q8, context 16K/32K, KV f16/q8, reasoning on/off и Vulkan/HIP проводить по одному фактору за раз.

Внутри серии одной модели чередовать обвязки по заранее сохранённому порядку, а не выполнять сначала все повторы одной и затем другой. Фиксировать seed порядка, режим питания, warm/cold состояние и паузы охлаждения. Время загрузки большой модели учитывать отдельно от времени агентной попытки; порядок и неудачи сохранять полностью.

## Отбор моделей без смешения факторов

Первая волна — малый контроль и приоритет 1 каталога. Вторая — приоритет 2, включая крупные MoE и dense-контроль. Приоритет 3 — ресурсные граничные случаи и сравнение поколений. Фактическая память имеет приоритет над номинальным классом 30B/70B/120B. Огромные модели в сверхнизком bit-rate и streaming экспертов с SSD не входят в основную серию: это отдельное исследование компромиссов.

Перед pilot исключаются только технически несовместимые конфигурации (OOM, протокол, недоступный backend); низкая скорость сохраняется как результат. Ресурсный preflight и фактическая невозможность загрузки не превращаются в agent task fail. Начатый агентный прогон, завершившийся таймаутом или ошибкой, остаётся неудачной попыткой в своей серии.

До 3 финалистов выбираются по заранее заданному порядку: независимый результат T002 (`pass`, затем `partial`, затем `fail`), затем меньшее время выполнения, затем меньший пик общей памяти. При неполных метриках не приписывать победу по неизвестному показателю. Один pilot — слабый screening signal; итог относится только к финалистам, а не доказывает глобальный рейтинг всех моделей. Дополнительно сохранить frontier «качество / время / память», чтобы большой медленный финалист не вытеснил практичный быстрый вариант.

Параметры sampling брать из model card, закреплять для каждой модели; между обвязками одной модели они одинаковы. Thinking/reasoning effort, max output и chat template — часть условий. Контекст означает полный input + output budget: baseline 16384 с зарезервированным output до 4096 токенов, включая reasoning, если сервер считает его в output. Фактический effective input budget проверяется на API и в обвязке. Приоритет model card не означает, что всем моделям следует принудительно назначать `temperature=0`.

## Обвязки и необходимая интеграция

Основные кандидаты на локальную серию — **Pi, mini-SWE-agent, OpenCode и OpenHands**. Это план интеграции на основе upstream возможностей; текущие адаптеры лаборатории по-прежнему настроены на облачные providers.

| Обвязка | Основание | Проверка до включения |
| --- | --- | --- |
| Pi | [Custom models / OpenAI-compatible](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/models.md) | Custom model registry, exact endpoint, роли, streaming tool calls и native turn bound |
| mini-SWE-agent | [Local models](https://mini-swe-agent.com/latest/models/local_models/) | API base, текстовый action protocol собственного DefaultAgent, неизвестная стоимость без выдуманного тарифа |
| OpenCode | [Custom provider](https://opencode.ai/docs/providers/#custom-provider) | OpenAI-compatible provider, явный context/output, usage и native tools |
| OpenHands | [LLM в SDK](https://github.com/OpenHands/software-agent-sdk) | Параметр base URL закреплённой SDK, streaming/tools и фактический iteration limit |

Codex — дополнительная ветвь только после проверки локального API/protocol на закреплённой версии. Claude Code, Antigravity, Copilot и Amp не включаются в основной локальный план без отдельного документированного и проверенного пути. Наличие модели в облачном каталоге не означает возможность отправить запрос к своему серверу.

План технической готовности, выполняемый **до** этапа 3:

1. Доверенный локальный inference service вне task workspace, без shell/tools и без mount репозитория со скрытыми проверками. У агента остаётся собственный Docker sandbox; его 2 GiB лимит не должен ограничивать model server.
2. Узкий proxy-маршрут к одному закреплённому адресу/порту сервера. В текущем `egress.mjs` private addresses специально запрещены. Нужен отдельный local endpoint policy с отказом в доступе к остальной LAN и административным API; общий SSRF/public-source фильтр сохраняется. Инференс не должен уходить на cloud fallback.
3. Для каждого адаптера явный local provider, endpoint, model alias, context/output и protocol. Если endpoint использует секрет, он поступает из `.env` через выбранный профиль. Dummy auth marker не является платным API key.
4. Поддержка local identity/metadata в `results/schema.json`, validator, prepare snapshot и compare. Сейчас схема этих полей не содержит; не добавлять произвольные поля вручную в `run.json`. Ключ сравнения должен включать hash весов, quant, template, backend commit, context, KV dtype, sampling, reasoning и аппаратный паспорт.
5. Синтетические интеграционные тесты bridge: успешный tool round-trip, отказ к другому IP/порту, oversized/error responses, таймаут и cleanup, смена alias/weights, неизвестный usage. Затем одна реальная pilot попытка с независимой оценкой и новая строка ledger для каждого добавленного компонента.

## Измерения и записи

Для backend-этапа сохранить: Linux/BIOS/driver snapshot; commit и build flags llama.cpp; GPU device/heap; weight repository/revision, имена всех shards, bytes и SHA-256; tokenizer/chat-template hash; model alias; quant; context, batch/ubatch, KV/state dtype, GPU layers/offload, slot count; sampling/reasoning; load time; TTFT; prompt/decode tokens/s; peak RAM и device allocations; swap delta; wall-clock; ошибки и raw logs. Единая RAM не суммируется дважды с GPU allocations. Prefill отдельно от decode, cold start отдельно от warm. Измерение max context должно действительно заполнить контекст, не ограничиваться запуском пустого сервера.

Дополнительно: результаты пяти protocol cases (обычный текст, streaming, tool-call → tool-result → final, ошибки/неизвестный tool, длинный контекст) по два повтора; reasoning отделяется от final, если архитектура его использует. Для mini-SWE-agent проверяется также его штатный текстовый action protocol; обвязка с таким протоколом не обязана использовать JSON function calling.

Агентные попытки остаются в `results/runs/<run-id>/` по основному [протоколу](method.md). Backend-пробы до расширения схемы сохраняются отдельно в `experiments/local-models/measurements/<probe-id>/` с собственными `metadata.json` и raw logs: они не выдаются за завершённые задачи или `run.json`. Плановые карточки не являются измерениями. Пока таких папок и файлов результатов нет.

Электроэнергия: если есть счётчик, фиксировать joules/Wh всей системы, idle baseline и способ измерения. TDP не заменяет измеренные watts. Отсутствие тарифа провайдера не делает локальный прогон бесплатным: отдельно считать inference fee (0 только при подтверждённом local-only), kWh, заданный пользователем тариф и при необходимости амортизацию. Неизвестные величины — `null` с причиной.

Для T001 использовать один замороженный source archive; иначе одновременно меняются web-данные. Для T003 текущий setup включает конфигурацию выбранной обвязки, поэтому разные harness дают разные входы: аудит не включается в причинное сравнение одной обвязки с другой. Первые 72 попытки T001/T002 — основа сравнения; 36 T003 — отдельная диагностика. Не читать скрытые проверки при разработке адаптера; оценщик работает вне agent container.
